# Changelog: astraeus

Versions follow [semantic versioning](https://semver.org). While the version starts with `0.`, the public API (the names exported from `astraeus`) may still change between minor versions; each change is listed here.

## Unreleased

Upgrading from 0.7.0, two behaviours change: the viewer no longer reads or writes the page address unless you pass `address: true` (T-223), and a `pacing` event rule in a scene with views slows playback only at the showing view's events (T-224). The other entries below only add.

First download of the packed example (`npm run measure:example`, `examples/hello-scene`, which now also carries two probes, three views, pacing and the camera-to-the-encounter host code): 1,659,659 bytes raw, 478,702 bytes gzip (code and styles loaded on first open), against 1,652,632 raw and 472,929 gzip at 0.7.0 (+7,027 raw, +5,773 gzip, most of it the new host API surface and the longer example).

- The host can read which object is selected and hear when it changes (O-054 T-247, G-016). `ViewerHandle` (from `mount` and from `AstraeusScene` `ref` and `onReady`) gains `selected` (the id of the object whose information is open; undefined before `ready`, after `unmount` and when nothing is selected) and `onSelect(listener)`, which calls `listener({ object?, timeUtcMs, cause })` only when the selection differs from the last report (the opening selection is read, not reported) and returns a stop function; the new type `SelectionChange` is exported. Read only: no setter. Migration: in an app built on 0.7.0, replace any reading of the viewer's object menu or a poll of the page for the selected object with `handle.selected` and `handle.onSelect(...)`; nothing else changes.
- The host can pause and play the viewer (O-054 T-246, G-016). `ViewerHandle` (from `mount` and from `AstraeusScene` `ref` and `onReady`) gains `playing` (undefined before `ready` and after `unmount`) and `setPlaying(boolean)`, which goes through the visitor's own play handler (one clock); `onChange` hears it with `cause: "host"`. A non-boolean, or a scene with `setTimeline({ none: true })` (no play control), throws `bad-timeline`; before `ready` or after `unmount`, `not-mounted`. Migration: in an app built on 0.7.0, replace any click on the play button or `rate` workaround for pausing with `handle.setPlaying(false)` and read `handle.playing`; nothing else changes.
- A scene is frozen once a viewer takes it (O-054 T-245, G-016). After `mount(element, scene)` or an `<AstraeusScene scene>` build, every `add*`, `set*` and `scene.camera` edit (`follow`, `lookAt`, `setReach`, `fitOrbit`) throws the new `SceneErrorCode` `scene-mounted` instead of being silently ignored; `stateOf`, `provenanceOf`, `missingData` and the camera getters still answer, and the same scene can be mounted again, also into a second element. A build that fails (an empty scene, a missing data package) leaves the scene editable, and `toDefinition` on its own does not freeze. Migration: in an app built on 0.7.0, build a new `Scene` instead of editing one already mounted, and pass it as the new `scene` prop or mount it again.
- One throwing listener no longer silences the others (O-054 T-244, G-016). `onChange` and `onEventZone` listeners (the handle's, the scene option and the React props) are all called through one helper: a listener that throws is reported to the page with `reportError` (else rethrown on a timer) after the rest have run. Migration: none needed; in an app built on 0.7.0, an error thrown in one listener now shows up as a page error instead of cutting off later listeners, so remove any try/catch kept only to protect them.
- Package ranges now state what was tested (O-053 T-230, G-016). The engine's `react` and `react-dom` peers are `>=19 <20` (all of React 19; they stopped at `<19.4`), checked by installing the latest React 19.x into the packed engine (`npm run check:react-consumer`). Each `astraeus-data*` package's `astraeus` peer is the engine's current minor, `>=0.7.0 <0.8.0` today, instead of `>=0.1.0 <1.0.0`. The engine now exports `./package.json`, as the data packages already did.
- Every `SceneErrorCode` now carries a doc comment that says what it means (O-053 T-229, G-016); the README error table is generated from them (`npm run api:errors`). The set of codes is unchanged; only the comments in the lock's `SceneErrorCode` signature differ.
- React apps get the same handle as `mount` (O-054 T-242, G-016). `AstraeusScene` takes a React 19 `ref` prop that receives the `ViewerHandle` (one object for the component's life, also across a rebuild with a new `scene`; reads `undefined` and calls throw `not-mounted` until drawn and after unmount), and `onReady` now receives that handle. `onReady` under React StrictMode fires once per build, after the viewer has attached (before, the replayed effect closed the link for good and it never fired); the `camera` prop is compared by value whatever the key order of a pose. `mount` and `AstraeusScene` build the handle with one shared helper. Migration: in an app built on 0.7.0, read and set through the handle from `ref` or `onReady(handle)` (the props stay as shortcuts); an `onReady` that took no argument keeps working.
- The mount handle has one shared type and an honest error before and after use (O-054 T-241, G-016). New exported type `ViewerHandle` holds every read, setter and signal of the handle; `MountedScene` is `ViewerHandle` plus `ready` and `unmount`. New `SceneErrorCode` `not-mounted`: any handle call before `ready` or after `unmount` throws it (was `missing-data`, which now means only missing data packages), and `ready` now rejects with it when `unmount` comes before the viewer is drawn (it used to stay pending or resolve unusable). Migration: in an app built on 0.7.0, catch `not-mounted` instead of `missing-data` for handle calls made before `ready` or after `unmount`, and handle (or ignore) a rejected `ready` after an early `unmount`.
- Errors follow one rule (O-054 T-240, G-016). A repeated `addActivity` id now throws `duplicate-id` (was `bad-activity`), like every other repeated id; a data package whose moon positions name a planet without a moon system now throws `SceneError("bad-data")` (new code; was a `RangeError`); a `lineFixedTo` stretch with no body is a `bad-trajectory` `SceneError` throughout; the sun-orbit code recognises its two internal range faults by named error classes (still `RangeError` subclasses) instead of by message text. Migration: an app that catches `bad-activity` for a repeated activity id should catch `duplicate-id`, and one that catches a `RangeError` from a bad data package should catch `SceneError` code `bad-data`.
- The host hears when playback enters and leaves a flyby (O-052 T-226, G-015). New `MountedScene.onEventZone(listener)` and `AstraeusScene` prop `onEventZone` call `listener({ event, type?, object?, entered, time, cause, via })` (`via` is `"time"` for playback or a seek and `"view"` for a view switch that showed or hid the zone, so a host restores a camera only for `"time"`) as playback crosses, or a seek or view switch moves across, the zone of a pacing `near` rule for an event the showing view has (`cause` `playback`, `visitor` or `host`); `MountedScene.eventZones` reads the active event ids. A zone already active when the viewer opens reports `entered` once after `ready`. New exported type `EventZoneChange`. The engine builds in no camera behaviour: the README's "camera to the encounter" example composes `onEventZone` with `setCamera` and `camera`. No new event field and no pacing option.
- The host can point the camera and read its pose (O-052 T-225, G-015). `MountedScene.setCamera(target)` and the `AstraeusScene` `camera` prop take `{ follow: id }`, `{ focus: id }` or a pose; `MountedScene.camera` (defined from `ready` on) reads the camera as a plain `{ focus, azimuthDeg, elevationDeg, distance }` value (the pose a view link carries), and `setCamera(handle.camera)` restores it. The object must be one the showing view shows; an unknown or hidden id or a malformed argument throws `bad-camera`, before `ready` or after `unmount` `missing-data`. New exported types `CameraPose` and `CameraTarget`. The engine moves no camera on its own.
- Pacing follows views (O-052 T-224, G-015): in a scene with `setViews`, a `pacing` event rule `{ near: { type, within }, rate }` now slows playback only near the events the showing view has; in 0.7.0 every view slowed at every event of the type. Spans apply in every view. A view switch that changes the paced speed eases to the new speed over about a second (log space, reported by `onChange` with `cause: "playback"`); seeking lands on the paced speed at once, and a speed the visitor or host picked still wins until `"auto"`. A scene without views is unchanged.
- The viewer leaves the page address alone unless asked (O-052 T-223, G-015). New `address` option on `mount` (`MountOptions.address`) and `AstraeusScene` (`address` prop), default `false`: off, the viewer reads no address parameter (`view`, `t`, `scale`, `up`, `show`, `stars`, `milkyway`, `milkywaybrightness`, `sky`, `labels`, `loop`, `markerpx`, `featurepx`, `sunglow`, `sunbrightness`, `sunglowscale`, `loadfade`), never calls `history.replaceState`, and hides the Developer tools' "Copy view link" button. Behaviour change from 0.7.0, which read and wrote the address regardless; pass `address: true` for it (the demo site does). With it on, a copied link in a scene with views also writes `show=<view id>`, and opening it shows that view (an unknown id opens the scene's `start` view). The README's new "Page address" section lists every parameter. A new test fails if source outside `src/app/address.ts` reads the address.
- `ready` means usable (O-052 T-222, G-015): `mount`'s `ready` resolves, and `AstraeusScene`'s `onReady` fires, only once the viewer has attached its clock, so `time`, `rate`, `view`, `setTime`, `setRate` and `setView` work straight after `await ready`. In 0.7.0 `ready` resolved about two frames earlier and `await ready; setView(...)` threw `missing-data`. A load failure still rejects `ready`; `unmount` before the viewer is drawn never makes it usable. No change to the handle's shape or error codes.

## 0.7.0 (2026-11-01)

First download of the packed example (`npm run measure:example`): 1,652,632 bytes raw, 472,929 bytes gzip (code and styles loaded on first open).

A probe followed as one path, close timeline markers each reachable, the picture-pack moon list documented (O-050), and views of one scene switched inside the viewer (O-051), from the fourth round of findings sent back by the outside interplanetary probe app built on 0.6.0 (G-014).

- Views of one scene (O-051 T-218, I-124, API half), no existing call changes. New `Scene.setViews([{ id, label, paths?, bodies?, events?, panels?, camera? }], { place, start? })` names views, each listing the paths, bodies, events and story panels it shows; anything no view names shows in every view. `toDefinition` resolves each view's membership once into `definition.views`. A bad list, id, place, camera or start throws the new `bad-view` code. New exported types `ViewInput`, `ViewsOptions`, `ViewCameraInput`. The viewer does not switch views yet (next steps). A scene without views is unchanged.
- The viewer shows the view choice (O-051 T-219, I-124, viewer half): one button per view in the top bar, or a row each in the switch panel, and in the phone drawer, the opening view pressed. Choosing a view hides the other views' paths, bodies, labels, picking targets, timeline events, story panels and story markers at once, from one hidden-id set the frame reads; nothing is rebuilt, and time, speed and playing state carry over. An object the view hides is dropped from the object menu, and a selection or follow on it is dropped, with the camera handled by the per-view camera rule of the next entry. A scene without views is unchanged. The per-view camera rule and the host's `setView` follow in the next entry.
- Each view steers the camera and the host picks the view (O-051 T-220, I-124, camera and host half). When a switch takes away the object the camera follows or focuses on, the new view's `camera` rule decides: `"stay"` (default) holds the camera where it is (target fixed in the scene, pose kept), stops following and closes that object's card; `"start"` takes the scene's opening framing; `{ follow: id }` / `{ focus: id }` takes that framing. A followed object still in the view is left alone. New `MountedScene.view` and `setView(id)` (unknown id or no views: `bad-view`; before `ready` or after `unmount`: `missing-data`), `AstraeusScene` prop `view`, and `ViewerChange.view` (only in a scene with views; `cause` `visitor` for the buttons, `host` for `setView`). A scene without views is unchanged.
- Proof on the packed package (O-051 T-221, I-124): `npm run check:node-consumer` builds three views on two made-up probe paths and a shared body from the packed package and asserts the resolved views, `start`, camera rules and every `bad-view` fault; the made-up `synthetic-views` scene is switched by a visitor and by a host `setView` at 1280x720 and 375x667, and the "stay" rule holds the camera still while the clock runs, checked by `npm run check:browser`.
- `addTrajectory`'s `lineFixedTo` also takes a list of `{ start, end, body }` stretches (O-050 T-213, I-125): each stretch of the line is drawn against its own body, so a flyby (Sun-fixed cruise, planet-fixed encounter, Sun-fixed cruise) is one path with one menu entry and card. Same span rules as `provenanceSpans`; a fault throws `bad-trajectory` naming the index. A single body id behaves as before.
- `lineFixedTo: "auto"` (O-050 T-216, I-125): the stretches are picked from the path's own samples. Each sample is fixed to the innermost scene body whose sphere of influence (`a (m / M)^(2/5)`, GMs from the catalogue) holds the probe, else the scene centre, so any flyby or orbiter is one path without working out switch times. Resolved once at mount or `prepare`; a body without a catalogue GM is skipped.
- Close timeline markers stay reachable (O-050 T-214, I-126): events, story panels and window peaks that sit under 22 px apart on the measured track gather into one numbered mark whose list opens each member as a full-size button; nothing gathers until the track has a measured width.
- Proof on the packed package (O-050 T-217, I-125 to I-127): `npm run check:node-consumer` builds a listed-stretch path, a `"auto"` path and a Moon-orbit path and asserts one menu object per path and the resolved stretches; the made-up synthetic journey draws its traveller against the Sun, Jupiter and the Sun again and adds three moon passes within nine hours of Jupiter's, checked by `npm run check:browser` (the camera stays on the traveller across both stretch boundaries; each gathered marker opens its own event at 1280x720 and 375x667).
- First download of the packed example (`node tools/measure-example.mjs`, after `npm run build`): 1,652,632 bytes raw, 472,929 bytes gzip at release, against 1,638,245 raw and 468,717 gzip at 0.6.0 (+14,387 raw, +4,212 gzip: the stretch drawing, sphere-of-influence resolver and marker grouping, +5,956 raw and +1,752 gzip as measured after O-050; the views, the view choice, the hide stage and the camera hold add +8,387 raw and +2,426 gzip, measured after O-051 T-221; the I-129 repair adds +44 raw and +34 gzip).

## 0.6.0 (2026-11-01)

First download of the packed example (`npm run measure:example`): 1,638,245 bytes raw, 468,717 bytes gzip (code and styles loaded on first open).

Every listed moon can be added by id (O-049, G-014), from a third finding sent back by the outside interplanetary probe app built on 0.5.1: Uranus's main moons had positions but no bodies.

- Every moon in the engine's moon lists (458 across Mars, Jupiter, Saturn, Uranus, Neptune and Pluto) now carries a sidereal orbit period from the JPL Planetary Satellite Mean Elements table (O-049 T-210, I-122), and a small generated lookup (`core/bodies/listedMoons`: id, label, mean radius, parent, period, data package, fit-set body) lets a later step add any listed moon by id without loading the full lists. Importing the lookup from the entry adds 17,716 bytes raw and 7,126 bytes gzip to the first download (`npm run measure:example`, measured with the lookup consulted from `addBody`); the full lists stay out of it.
- `scene.addBody(id)` takes every moon in the moon lists, not only the ready-made ones (O-049 T-211, I-122). One rule: the listed moon becomes a grey sphere at its JPL mean radius (the picture pack's picture when it holds one under the moon's id), positioned from its planet's fits in `astraeus-data-<planet>`, with `{ orbit: true }` drawing one lap of its JPL period about the planet; a moon without a period throws `no-orbit`, a missing package `missing-data`, a window outside its fit years `out-of-span`. The detailed moons (Io to Callisto, Saturn's seven, Triton, Charon, Phobos, Deimos) keep their own definitions. A moon is defined only when a scene adds it, so an unused moon costs nothing at run time. New `listedMoons(planet?)` lists every addable moon with the data package it needs (`requires`); the `unknown-body` message names the built-in ids and `listedMoons(planet)` rather than hundreds of ids. With the lookup used, the first download of the packed example is 1,638,245 bytes raw, 468,717 bytes gzip (+19,682 raw, +7,617 gzip on 0.5.1; re-measured after T-212 with `npm run build` and `node tools/measure-example.mjs`).
- Proof on the packed package (O-049 T-212, I-122): `npm run check:node-consumer` adds Miranda and Titania by id with `{ orbit: true }` and lists Uranus's moons; the made-up synthetic journey now passes Uranus on 24 January 1986 and adds its five main moons, checked by `npm run check:browser`. No change to the package's code or size.

## 0.5.1 (2026-10-31)

First download of the packed example (`npm run measure:example`): 1,618,563 bytes raw, 461,100 bytes gzip (code and styles loaded on first open).

Near planets stay visible and ringed planets show their rings (O-048, G-014), from a second round of findings sent back by the outside interplanetary probe app built on 0.5.0.

- A planet or moon near the camera now stays visible however far the camera has zoomed out (O-048 T-204, I-117). The renderer uses a logarithmic depth buffer, so a Sun-centred scene whose far plane reaches a 170 AU path no longer loses Saturn at 0.01 AU to depth precision. Every custom shader in the engine carries the log-depth chunks, and a test fails for one that does not.
- Jupiter, Saturn, Uranus and Neptune now carry their rings in their one catalogue definition (O-048 T-205, I-118), so a scene that adds the planet through the public API draws the rings with their NSSDC fact-sheet source; the ring bands and the ring look sliders are unchanged. The planets demo no longer attaches rings itself. First download of the packed example (`npm run measure:example`) grows from 1,608,313 to 1,617,005 bytes raw and from 457,901 to 460,652 bytes gzip (the ring data now ships with the engine).
- `addBody(moon, { orbit: true })` draws the orbit line of any catalogued moon, not only the Moon and Io (O-048 T-206, I-119). One rule: one lap of the period the moon's catalogue definition carries (`orbitPeriodDays`, read once from its mean-element record), drawn about its planet; the Moon and Io draw as before, and a moon with no period (Phobos, Deimos) throws `no-orbit`. First download grows by 786 bytes raw, 243 bytes gzip (1,617,005 to 1,617,791 raw; 460,652 to 460,895 gzip).
- `addEvents` takes an optional `object` (a body or trajectory id) per event (O-048 T-207, I-120): the timeline's Go to, Previous and Next seek to the event and frame that object as `camera.lookAt` does; an event without one seeks as before, and an `object` the scene lacks throws `bad-event` naming the event and the id. Only code already in the first download changed; size is not re-measured.
- Overlapping labels no longer flicker at fast playback (O-048 T-208, I-121). One rule for every label: a label hidden by an overlap needs 14 px more clearance than the plain 6 px gap before it shows again, so two labels crossing swap winner once per crossing; the selected object's label still always wins and labels switched off stay hidden. Layout only; no State change and no new files in the package.

## 0.5.0 (2026-10-31)

First download of the packed example (`npm run measure:example`): 1,608,131 bytes raw, 457,845 bytes gzip (code and styles loaded on first open).

A historical probe journey can be told end to end (O-047, G-014), from findings sent back by an outside interplanetary probe app built on 0.4.0.

- Far-away markers and group dots are drawn round instead of square (one shared `dotMaterial`; size and colour unchanged).
- A path reaching past the planets can be zoomed out to whole (O-047 T-203, I-114). In a Sun-centred scene with a path about the Sun and no `camera.setReach` or `camera.fitOrbit`, the farthest zoom-out and the far plane now widen to cover twice the path's farthest distance from the Sun for the canvas shape (it never narrows the old default, and a declared reach still wins); proved with a path to 170 AU on a desktop and a phone shape. Before, the default stopped near the planets and the far plane (5,000 Earth radii) cut the path off.
- Fixed: a moon's orbit ring is centred on the clock, so at the last instant of the timeline it asked for positions the page had not loaded (a chunk error every frame). The loader now also fetches the year after the timeline's end for each moon where the data package ships it.
- Changed: playback in a scene with a timeline bar that does not loop now stops on the end (or start, at a negative speed) of the timeline instead of running past it. Before, the clock kept going and moons were asked for positions the page had not loaded, an error every frame.
- A path can carry different provenance along its length (O-047 T-198, I-113). `addTrajectory` takes `provenanceSpans`: a sorted, non-overlapping `{ start, end, provenance }` list inside the path (the shape of an activity's `provenance`), and the info card shows the span the clock is in; a gap, or no list, shows `provenance` (or the illustrative default) as before. Faults throw `bad-trajectory` naming the index.
- Playback can slow down for encounters and speed up for cruise (O-047 T-201, I-112). `setTimeline` takes `pacing`: spans `{ from, to, rate }` and event rules `{ near: { type, within }, rate }`, with optional `ramp` seconds; the speed eases between pieces (log-space smoothstep, a pure function of the time, so loops and seeks land right). The speed menu gains **Auto** in a scene with pacing; a speed a visitor or the host picks wins until Auto or `setRate("auto")` (new on the `mount` handle and the `AstraeusScene` `rate` prop; `bad-timeline` without pacing). Where pieces meet (a span and an event rule, or two event rules, either containing the other) the slowest speed applies, whatever order they are listed in. Overlapping spans and a rule whose event type has no events throw `bad-timeline` naming the field. New exported type `PacingInput`.
- A host page can read and set the viewer's time and speed (O-047 T-197, I-099). The `mount` handle gains `time`, `rate`, `setTime(time)`, `setRate(rate)` and `onChange(listener)`, and `mount` takes `onChange`; `AstraeusScene` gains `time`, `rate` and `onChange` props. `onChange` hears `{ time, rate, playing, cause }` for playback, a visitor's use of the timeline and the host's own calls. `setTime` outside the timeline throws `bad-time`; `setRate` takes only a speed the timeline offers, else `bad-timeline`; setting before `ready` throws `missing-data`. New exported types `ViewerChange` and `RateSource`.
- Changed: the speed menu shows exactly the `rates` a scene gives (I-106). Before, 1x, 1 hour, 1 day and 1 week per second were always added. A scene that gives no `rates` still offers 1 minute, 1 hour and 1 day per second. A scene that relied on the added speeds must now list them.
- Orbit lines and `camera.fitOrbit` now work for every planet (O-047 T-196, I-111). One rule, chosen by data coverage and never by name: one full turn of the body's own positions where they cover a whole turn from the opening time (the turn search now reaches Saturn's 29.5 years), else the two-body ellipse osculating at the opening time (Uranus, Neptune), whose info card says so and that perturbations are not drawn. The farthest distance for `fitOrbit` is worked out once in setup (at `toDefinition`, or at `prepare` once the planet series are in), so a failure reaches the host once through `ready`, not per frame.
- A body's positions can cover its own years (O-047 T-195, I-110 engine half). A moon-fit `index.json` may give each body a `span: { fromUtc, toUtc }` (optional; an index without one reads as before, the six shipped data packages are unchanged), and the engine answers each body only inside its own span and its centre's. The importer `tools/import/horizons-moons.mjs --only ... --from ... --to ...` merges a longer-span rebuild of chosen bodies into an existing index.
- New `SceneError` code `out-of-span`. A scene whose timeline reaches outside the years a loaded moon's data (or the built-in planet series, 1950 to 2045) covers now fails once, as `ready` rejecting at mount, naming the body, the data package and the span, instead of throwing on every frame.
- The main moons and each planet's system fitted back to 1950 (O-047 T-200, I-110 data half). `astraeus-data-jupiter` (Io, Europa, Ganymede, Callisto), `-saturn` (Mimas, Enceladus, Tethys, Dione, Rhea, Titan, Hyperion, Iapetus, Phoebe), `-uranus` (Miranda, Ariel, Umbriel, Titania, Oberon) and `-neptune` (Triton, Nereid) now answer from 1950-01-01, each with its planet; every other moon keeps 2010 to 2030. Worst fit error 0.59 m or less per moon, 0.05 m or less per planet; moon about planet through the provider against Horizons 0.53 m or less. The packages grew: Jupiter 22.9 to 30.9 MB packed, Saturn 40.0 to 53.5 MB, Uranus 32.6 to 40.6 MB, Neptune 17.8 to 18.5 MB (a page still downloads only the years it shows). The built-in planet series (`planets.json`) now runs 1950 to 2045 (was 1969), 329 kB to 432 kB raw (220 to 279 kB gzip); the example's first download is 1,608,131 bytes raw, 457,845 gzip (was 1,594,919 and 453,695). A mapped moon's `accuracy.validUtc` and its position note follow the span of its own data.
- Fixed: the fitted moons' time-scale table before 1972 followed monthly samples, so a Jupiter- or Saturn-centred position in 1961 to 1972 could be 1 to 7 km off in time terms; it is now sampled daily with a piece per step and per straight stretch (within 10 microseconds), and the end-to-end check back to 1950 is within 0.6 m.
- Fixed: asking the ephemeris for a body's bounds threw for Pluto's data, whose last chunk ends a day past its time-scale table.

## 0.4.0 (2026-10-31)

First download of the packed example (`npm run measure:example`): 1,594,919 bytes raw, 453,695 bytes gzip (code and styles loaded on first open).

A recorded path can now cross the solar system (O-046, G-013), from findings sent back by an outside Voyager app built on 0.3.0.

- `addTrajectory` says which frame its positions use (I-097): equatorial J2000 (EQJ) about `center`, as before. A new `plane: "ecliptic-j2000"` option takes ecliptic vectors as JPL Horizons publishes them and rotates them to EQJ once on the way in (samples and provider states), so drawing, `stateOf` and readouts agree. A bad `plane` throws `bad-trajectory`.
- A path can cross the solar system (O-046). `addTrajectory` is now accepted in a Sun-centred scene (it threw `bad-trajectory`), and a new `lineFixedTo` option names the body the path's line is drawn against at each sample's own time (default the scene centre; `"sun"` for a probe). A `lineFixedTo` body the finished scene does not hold throws `bad-trajectory`. Paths in Earth-centred scenes draw as before.
- Behaviour change (O-046): `addTrajectory`'s `center` now defaults to the scene's centre (its first body) instead of always `"earth"`. Scenes whose first body is Earth (Apollo 11, the hello example) are unchanged; a scene whose first body is neither Earth nor the Sun now reads its paths' positions from that body, so add `center: "earth"` to keep the old reading. A path added before any body follows the first body added; with no catalogued first body the default stays Earth. Found when a made-up probe given from the Sun missed Earth by a wide margin in a Sun-first scene.
- `solarSystemScale` is exported beside `trueScale` and `readableScale`, and `setScale` accepts it (I-098), so a Sun-centred scene with an enlarged body can open on the Solar system view. In any other scene `toDefinition` throws `bad-scale`.
- Example and check (O-046 T-193): the README shows a made-up Sun-centred probe path ("A probe across the solar system"); the repository's dev site opens a fuller made-up one at `?experience=synthetic-probe` (not in public builds). A provider path's `orientation` is not rotated by `plane` (documented limit).
- A path's own name shows (I-100). Its label was limited to 4 scaled units from the camera, so it never showed at a normal view; it now has the same reach as a body's label (none in a Sun-centred or fitted scene, otherwise the camera reach, at least 500) and follows the `labels` switch. In Earth-centred scenes a path's label now shows as far out as a body's; give it `labelReach` to keep a shorter reach (Apollo 11 keeps 4).
- New `labelReach` option on `addBody` and `addTrajectory`: a positive number (the camera's `distance` units) that limits how far from the camera that label shows, replacing the shared rule for that item; a bad value throws `bad-body` / `bad-trajectory`. Apollo 11 sets `labelReach: 4` on its paths so they behave as before.
- Wording only (O-046): the `addActivity` error for a missing unit now suggests `"events per hour"` instead of `"meteors per hour"` (the engine names no shower, ARCH-06); the doc comment's example changed the same way.
- Labels (I-108): as before, the label of the selected object (the one `camera.follow` or `camera.lookAt` opens on) always wins a collision with another label, so follow a path to keep its name shown on a small screen; other labels keep their priority order (bodies before paths). A scene's labels also stay hidden until the first layout places them, so none shows unplaced for a moment after load.

## 0.3.0 (2026-10-29)

First download of the packed example (`npm run measure:example`): 1,592,336 bytes raw, 453,513 bytes gzip (code and styles loaded on first open).

- The Milky Way is a new picture (I-026), no API change. The sky's Milky Way band is now the starless Gaia EDR3 render by Kevinmloch (CC BY-SA 4.0, 3840x1920), softer against the catalogue stars; it replaces the two ESO halves. The picture ships in `astraeus-data` (see its changelog) and is dimmed in the viewer; `milkyWayBrightness` still scales it, and it stays off by default.

- Answers for sites (O-045). `Scene.stateOf(id, time)` now answers for every body in the scene (ready-made bodies, moons, elements bodies), not only `addTrajectory` paths; they answer at any date, only a path refuses a moment outside it (`bad-time`), and a planet answers once the planet series are loaded (`missing-data` before). Its unknown-body message now reads "no body or trajectory with that id". New `Scene.provenanceOf(id)` returns the body's `Provenance`, which gains optional `accuracyClass` and `maxErrorFraction`: built-in Swift-Tuttle's is measured (0.00857); an elements body's is the limit of its class (0.01 approximate, 0.05 indicative), an upper bound and not a measured figure. New root exports: `APPROXIMATE_LIMIT_FRACTION`, `INDICATIVE_LIMIT_FRACTION`, `classifyPositionError` and `parseElementsBodyRecord`.

- Fit the zoom-out to an orbit (O-045). New `camera.fitOrbit(body)` sets the farthest zoom-out so the body's whole orbit fits the canvas from any direction, and re-fits when the canvas changes shape; the far plane is 2.5 times the reach. `setReach` and `fitOrbit` set the same limit, the later call wins. The opening view is unchanged except that it is clamped to the limit like any other. Labels are not limited in a fitted scene. `SceneError` `bad-camera` for a body that does not circle the Sun.

- Event labels (O-045). New provenance source type `"modelled"` (shown as "Modelled"). `addEvents` events take their own `provenance`, which wins over the batch's. Batch and per-event provenance are now validated: a malformed one throws `bad-event` (the batch one was not checked before). A group's info card shows "illustrative" as its source type, with the elements' type in the accuracy sentence (documented).

- Visible change (O-045). A body added with `addBodyFromElements` now has a live "Distance from Sun" row on its info card, and in the Geminids demo the Sun's card also lists "Distance to Phaethon".

- A better guest in a host page (O-044). `mount` and `AstraeusScene` no longer change `document.title`. The viewer's Escape handlers (story panel, phone drawer, switch panel) ignore a keydown the host already stopped with `preventDefault()`. The mount element and the `AstraeusScene` wrapper get `isolation: isolate`, so the viewer's `z-index` values (0 to 9) stay inside it; a `style` you pass to `AstraeusScene` can override it, and `mount` does not restore the element's old `isolation` on `unmount`.

- Node loading (O-044), no API change. The package's JSON imports now carry `with { type: "json" }`, and the root export has a `node` condition (order: types, node, import) that points at copies without the stylesheet import, so Node and Vitest's Node environment import `astraeus` with no inline setting. Bundlers keep the normal build. jsdom and happy-dom Vitest environments also take the `node` condition, so they do not load the viewer's CSS.

- Default time (O-044). A scene with no `setTime`, no `setTimeline` window and no trajectory now opens on the current time with a window of a month around it. This includes `setTimeline({ none: true })` with no `at`, which opens on the current time too (new in O-044; it was not changed in O-045).

- Phone story panel (O-044). On a phone, a wheel or two-finger pinch over an open story sheet zooms the scene behind it (the sheet has `touch-action: pan-y`).

- Documentation (O-044). The README says who needs `astraeus/style.css`, why a plain-JavaScript page still needs React, how story panels open and pause, that `camera.setReach(d)` also sets the far plane to 2.5 times `d`, and how to reload on `vite:preloadError`; `addStoryPanels`, `StoryPanelsInput` and `setReach` doc comments say the same.

- The Moon now shows libration (I-091), no API change. Its orientation was a plain tidal lock; it is now the IAU mean-Earth rotation model with its libration terms (Archinal et al. 2009 report, as saved in NAIF pck00011), so the Moon nods and sways by up to about 8 degrees as it does in the sky. Against JPL Horizons at seven dates from 1969 to 2050 the sub-Earth point and pole agree within 0.01 degrees (about 0.3 km on the surface); a surface place can no longer sit up to 8 degrees (254 km at Apollo 11's touchdown) from its true spot. Moon-surface features and mesh textures move accordingly.

- Documentation only: `addGroup` states that a `center` that is not a catalogued body throws `unknown-body` (a catalogued one missing from the scene throws `bad-group`), and `setTimeline` states that `loop` is ignored with `{ none: true }` or without a timeline. No behaviour changes.

## 0.2.0

The story layer: a scene can now carry your own bodies from orbit elements, orbit lines for any body circling the Sun, timed events, story panels, groups of many objects, an activity curve, display switches and a looping timeline, through `mount` or the new React component `AstraeusScene`. Every public name is documented at <https://astraeus.anipatke.com/api/>. Two changes can affect a 0.1 app: React, react-dom, `@react-three/fiber` and three are now peer dependencies (React 19 needed), and camera preset ids are now `focus-<id>` and `follow-<id>` (both below).

- Lighter first download (O-043), no API change. The Developer drawer's panels (settings, debug readout, frame-rate graph) are a separate file loaded only when the Developer switch is turned on: on the packed example the code loaded on first open went from 1,603,283 to 1,589,850 bytes (458,257 to 454,211 gzip). If that file cannot be fetched (offline, or a tab left open across a redeploy), the drawer says so and asks for a reload; the rest of the viewer keeps working.

- Gaps found rebuilding a shower (O-042 T-177), no existing call changes. A Sun-centred scene with an enlarged body (`addBody(x, { enlarge })`) now offers the viewer's "solar-system" scale (true distances, the named bodies enlarged) as its second scale choice in place of the readable scale, which does not enlarge; scenes without enlargement are unchanged. A Sun-centred scene with planets (orbit lines, or a group clumped near a planet) now works through `mount`, `AstraeusScene` and `prepareScene` without the caller loading the planet series: the lines and clumped groups are drawn once `prepare` has loaded them. `addGroup`'s `clump.near` accepts a body added with `addBodyFromElements`, and `addGroup` takes `refillSliceMs` (0 or more; `bad-group` otherwise).

- Activity, looping and view settings (O-042), no existing call changes. New `Scene.addActivity({ id, label, unit, start, end, samples, peak?, provenance?, ... })` gives the timeline a rate curve (the glow) with its peak and the source of each stretch; a group takes `readouts: [{ kind: "rate" }]` for a live rate bar on its card (unavailable outside the activity). `setTimeline` takes `loop: true`; `camera.follow` and `camera.lookAt` take `up: "ecliptic"`; new `camera.setReach(distance)` sets how far the viewer can zoom out (labels reach as far). New `SceneError` codes `bad-activity` and `bad-camera`; a rate readout naming no activity is `bad-readout`. New exported types `ActivityInput`, `ActivitySampleInput`, `ActivitySourceInput` and `GroupReadoutInput`.

- Sun-centred scenes (O-042), no existing call changes. `addBody(x, { orbit: true })` now also draws one full turn round the Sun of any body that circles it when `sun` is in the scene (planets, Earth's year; was `no-orbit` for all but the Moon and Io). New `Scene.addBodyFromElements(record, options?)` adds your own body from published orbit elements with their source and accuracy (`bad-element` names the bad field); `addBody` takes `enlarge` (planet drawn that many times larger in the readable scale; `bad-body` below 1) and `showLabel: false` (label starts off). A scene whose first body is the Sun sets no label reach, so labels do not fade when zoomed out, and refuses `addTrajectory` at `toDefinition` with `bad-trajectory`. New exported type `ElementsBodyRecord`.

- Groups of dots (O-042), no existing call changes. New `Scene.addGroup({ id, orbits, ... })` draws a list of orbits (each with its own id, shape and tilt) as one group of dots: one colour (`color`), dot size (`dotSizePx`), menu item, info card, provenance and known limits. The dots are placed along their orbits by an even spread shuffled by `seed`, optionally with a share clumped near a body (`clump: { near, fraction, widthDeg }`); `refillAfterMs` sets how often the dots are placed again. The group's id joins the camera menu (`focus-<id>`, `follow-<id>`) and can be named by a story panel's `object`. New `SceneError` code `bad-group` (empty list, bad or unbound orbit, bad colour or clump, a centre or clump body not in the scene); a repeated id is `duplicate-id`. New exported types `GroupInput`, `GroupOrbitInput` and `GroupClumpInput`. `examples/hello-scene` draws a made-up ring of 40 dots.

- Display switches (O-041), no existing call changes. New `Scene.setSwitches({ orbitLines?, labels?, milkyWay? })` places each switch on the top bar, in one switch panel opened from the bar, or only in the Developer drawer, and sets whether it starts on; a bad name, place or `on` throws `bad-switch`. Each placed switch drives the same state as its Developer-drawer buttons. New exported type `SwitchesInput`. With nothing placed the bar is unchanged. `examples/hello-scene` places two.

- Story calls (O-041). One visible change to existing behaviour: camera preset ids are now `focus-<id>` and `follow-<id>`, and the camera menu is built automatically, with a Focus and a Follow entry for every body and path; the Sky item is no longer listed in any object menu. `addTrajectory` takes `description`, `knownLimitations`, `anchors` (labelled dots where the data was published; a time outside the path throws `bad-anchor`) and `readouts` (info-card bars: `range`, `speed`, `distance`, `altitude`); `addBody` takes `description`, `color` (a hex colour for the info card and label) and `knownLimitations` (a list of non-empty texts shown with the provenance); a bad `color` or `knownLimitations` throws `bad-body`. New `Scene` methods: `addEvents` (timed events with optional `provenance`; `bad-event`), `addStoryPanels` (panels at a time, event or anchor; `bad-panels`), `setTimeline` (span, speeds, opening speed, or `{ none: true }` for no timeline; `bad-timeline`), `stateOf` (state of a path at a moment) and `camera.lookAt` (opening view without following). `setScale` takes `{ only: true }` to offer one scale. `examples/hello-scene` now uses all of them.

- An API reference page is published at <https://astraeus.anipatke.com/api/>, generated from the public types and doc comments; the package `homepage` points at it. Every export now has a doc comment (a test keeps it so). No change to the API.

- New export `AstraeusScene` (with its props type `AstraeusSceneProps`): a React component that draws the same viewer as `mount`, `<AstraeusScene scene={scene} data={[...]} onReady onError />`. It rebuilds when the `scene` prop changes and cleans up on unmount.
- Needs React 19 and `@react-three/fiber` 9.8.2 or later: `react`, `react-dom`, `@react-three/fiber` and `three` are now peer dependencies, not dependencies, so the host app's own copies are used and installed once. Install them beside `astraeus`. No change to the public API.
