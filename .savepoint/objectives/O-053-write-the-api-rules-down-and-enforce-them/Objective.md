# O-053: Write the API rules down and enforce them

## Outcome

Every Guardrails Public API rule (API-01 to API-07) that can be mechanised has a check in the normal test run, with today's breaks on per-check allowlists that may only shrink; the docs and package metadata the review found stale are honest; and from here on a change that breaks an API rule fails a test.

## Why

G-016 chunk 1. The rules are written (Guardrails Public API, Design "Public API shape", 2026-11-01); without checks the next four Objectives could reintroduce what they fix (owner's "strategic fix first": fix the rule that allowed the trap and mechanise it; ARCH-06 is the worked example).

## Success Conditions

Settled with the owner, 2026-11-01 (session api-review-20261101): principles accepted through D1–D10 and the plan summary "Yes, go ahead".

- **API-surface lock (API-01).** A checked-in lock of the root exports (values and types) and of each published package's `exports` map, built on the existing `collectExports` (`packages/astraeus-site/tools/site/api-reference.mjs`); a change without updating the lock fails. A reachable-type check fails when a type reachable from the root is declared outside `src/api/` unless allowlisted (today: the internal `ExperienceDefinition` through `toDefinition`, and the unexported input types the review names).
- **Front door for our own code (API-01, D6).** `packages/astraeus-site/tests/packageBoundaries.test.ts` counts deep imports into the engine per package; counts may only go down.
- **Public-type lint (API-04).** Over the public `.d.ts`: unit suffix on numeric fields unless on the unitless allowlist; `centre` banned; time-like fields typed `TimeInput`; spans `{ start, end }`; frame fields `plane`; no `unknown`/`any` reachable from the root. Today's cases on a shrinking allowlist naming the review finding that fixes each.
- **Errors (API-05).** A scan fails on a `throw` in `src/api/` that is not a `SceneError` (allowlist: today's `api/data.ts` RangeError) and on matching an error by message text; the README error table is generated from `SceneErrorCode` and a test keeps it in sync.
- **Settings mapping (API-06).** A test lists every address setting read through `src/app/address.ts` and fails when one has no public setting key, with today's ones allowlisted for O-056.
- **Viewer isolation scans (API-03).** An id-literal scan over `src/shell/` and `src/app/` and a CSS selector scan over `app/style.css` (every selector under the viewer's root class), today's cases allowlisted for O-055.
- **Honest versions and docs (API-07, D7).** Each data package's peer range is the engine's current minor, checked by `check:pack`; the engine's React peer covers all of React 19 with a CI build on the latest 19.x; the engine exports `./package.json`; stale "0.2 preview" banners and the React `style.css` note are fixed; the README API rows include `address`; the two camera doc comments C-136 noted are corrected; README API tables are checked against the types by a test.
- **Proof.** Each check is shown failing on a planted break and passing on the tree (TEST-02 style); the allowlists name a finding (F-number) or Objective per entry. No behaviour change to the viewer.

## Architectural Considerations

Checks run inside the normal `npm test` (or `check:pack` where they need packed output), never as a separate manual step. Allowlists live next to their checks as data, one entry per break with a reason and the Objective expected to remove it. The lock is generated by a script and reviewed in diffs; it is not hand-written. No public API change in this Objective other than the `./package.json` export and the React peer range.

## Boundaries

**Out of scope:**
