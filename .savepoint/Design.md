# Astraeus — Design

## Architecture

Astraeus is a TypeScript astronomy engine with a scientific core, a reusable asset layer, React Three Fiber presentation and a generic viewer shell. The site and demos live in separate packages. Absolute UTC feeds physical state in EQJ kilometres; scale policies, floating origin and render-axis conversion act downstream and never change scientific State. The engine imports no other workspace package. Guardrails owns the layer, naming, provenance and reuse constraints.

This overview describes current architecture. Detailed contracts and dated reconciliation records are linked below; load only the relevant sections. Planned work belongs in Objectives, verification results in Tasks and Checks, and original owner intent in Idea.

## Interfaces and Data Flow

### Overview

`Scene` is the public story-building API. `prepareScene` converts it to the existing `ExperienceDefinition` and loads its data; both `mount` and the exported React `AstraeusScene` use that path. React 19, React DOM, Fiber and Three.js are published peer dependencies. The API reference is generated from `src/api/index.ts` exports and their doc comments; missing export documentation is tested.

### Scene and host-link split

Scene and host-link split (O-058, no behaviour change; `tests/scenePin.test.ts` pins the scene output): `Scene` holds one plan per concern (paths, bodies, groups and activities, story, timeline, views, camera) and `assembleScene` joins them into the `ExperienceDefinition`; a plan never imports the `Scene` and takes the ids it needs as callbacks, with type-only imports of the public input types from `scene.ts` (accepted type-only cycle). The host link keeps one public `ViewerLink` split by concern (clock, views, camera, zones) over a shared accessor. The two parsers the API reads (story panels, start view) live in `core/` so `api/` stops importing display code; `tests/apiImports.test.ts` limits the remaining `api/` imports of `shell/` and `app/` to a reasoned allowlist, and `tools/api-rules.mjs` covers story panels through the type walk (its parser-reading special case went in O-057 T-278). The demos' deep imports of the old `shell/storyPanels` and `app/viewLink` paths keep working through the re-exports until O-059 moves them onto the public API.

### One handle, one lifecycle

One handle, one lifecycle (O-054, G-016; T-240 to T-249): `ViewerHandle` (`api/viewerHandle.ts`, exported type) holds every read, setter and signal; `MountedScene` is `ViewerHandle` plus `ready` and `unmount`. `viewerHandleOf(link)` is the only builder of the handle: `mount` makes one per call and `AstraeusScene` one per component life (given through the React 19 `ref` prop and `onReady(handle)`, the same object across a rebuild with a new `scene`), so the two embedding paths cannot drift; `tests/lifecycle.test.ts` runs one suite against both. Errors: before `ready` or after `unmount` every read is undefined and every call throws the new code `not-mounted` (`missing-data` now means only missing data packages); listener registration (`onChange`, `onEventZone`, `onSelect`, `onCameraChange`) is exempt, never throws at any time and delivers nothing after `unmount`. `ViewerLink.whenAttached()` rejects with `not-mounted` when `close()` comes before the attach (so `ready` always settles); `ViewerLink.reopen()` takes a closed link back into use for a host effect that was cleaned up and replayed (React StrictMode) before the viewer drew, while a real unmount leaves it closed. The React driver in `lifecycle.test.ts` commits through `flushSync`, which fixed the T-243 StrictMode flake (30 of 30 runs); it is test-only, not architecture. The same T-240 error rule is reflected: a repeated `addActivity` id is `duplicate-id`, a data package whose moon positions name a planet without a moon system is `bad-data` (new code), and the two internal range faults of the sun-orbit code are named error classes in `core/`. Listeners: `api/listeners.ts` is the one helper that calls a set of listeners so a throwing one is reported (`reportError`, else rethrown on a timer) after the others have run; the clock, zone, selection and camera parts all use it. Scene freeze: `prepareScene` marks the scene in a module `WeakSet` (`api/sceneFreeze.ts`, so the public surface gains nothing) and every mutator of `Scene` and `SceneCamera` throws `scene-mounted`; reads (`stateOf`, `provenanceOf`, the scene reads, camera getters) still answer, a scene may be mounted again, and a failed build leaves it editable. Host signals (each a separate part of `ViewerLink`, none of it State, ARCH-02): `ViewerControl` gains required `playable` and `setPlaying` (`viewerPort.ts`; the handle's `playing`/`setPlaying` go through the visitor's own play handler, one clock, `bad-timeline` without a play control); `ViewerState` gains optional `selected` and the link has a fifth part `viewerSelection.ts` (`selected`, `onSelect`, `SelectionChange {object?, timeUtcMs, cause}`; the field is `timeUtcMs` per API-04, as `ViewerChange.timeUtcMs` also is since O-057; a selection dropped because time or the view moved takes the cause of whatever last moved them: `ViewerLink` keeps the cause of the last published clock/view change, and every shell selection path names its origin, a required `SelectionOrigin` argument of `onSelectionChange` (`"visitor"` for the menu, a pick, a preset or a marker; `"move"` for the fallback drop and a view rule's framing target, so a new path cannot omit it), so `onSelect` agrees with `onChange` (`host` for `setTime`/`setRate`/`setPlaying`/`setView`, `playback` for the clock running, `visitor` for the visitor's own moves; I-137); there is no separate selection-cause flag); `ViewerCamera` is stateful (last reported pose, report time, listeners) and is the fourth part `publish` calls (clock, zones, selection, camera), so `onCameraChange` rides the existing 100 ms viewer publish with no new frame-loop work and reports a pose only when it differs, at most about ten times a second. Unawaited `ready` (owner decision, 2026-11-01, "Only hide the expected 'taken down early' case"): `mount` marks `ready` handled only when it rejects with `SceneError` `not-mounted` (an early `unmount`), so a host that never awaits it gets no unhandled rejection for that; any other rejection, such as a failed load, stays unhandled until someone awaits `ready`, as before. Allowlist growth is judged per finding (Decisions, "Allowlist growth counted per finding").

### Host calls land in order

Host calls land in order (O-061, G-017; T-284 to T-288): after `ready` every host call takes effect or throws, in call order, the last host call winning (README "Host calls"). The camera keeps a host request in its own slot, `controls.hostCameraRequest` (set by `App` on a host `setCamera`, reset by `chooseView` at each view switch): `openFirstFrame` (`app/sceneCamera.ts`) still clears any other request at the opening but keeps the host's, and `applyViewRule` in `AstraeusShell` skips its own hold or framing request when the shell's `hostCameraSet` prop says the host set the camera since the switch, so a view rule is a default a later host call replaces (it still applies its selection change). A view's `camera` framing takes `always: true` (`ViewCameraInput`, `api/views.ts`; anything but `true` throws `bad-view`) to apply the rule on every switch to that view; without it the rule applies only when the switch takes away the followed object. Story panels have one seek re-base: the shell hands `story.noteSeek` (`useStoryPanels`, `CrossingTracker.rebase`) to `App` as `storySeekNote`, and both the visitor's seek and the host link's seek (`App.hostSeekTo`, then `seekTo`) call it, so a host `setTime` opens no panel by crossing. `ViewerHandle.setSelected(id | undefined)` (`api/viewerSelection.ts` through `ViewerLink`, ids checked against `cameraTargets()` as `setCamera` checks them, new code `bad-selection`) sets `controls.selectedObjectId` at once and queues a `selectRequest` the shell applies after its view-switch effect, opening or closing the object's card as a visitor's menu choice does without moving the camera; `App.updateSelectedObject` ignores the shell's older choice while that request is pending. `ViewerLink.publish` re-reads the viewer state after a nested publish, so a host call made inside an `onChange` report does not leave the rest of that report on the older reading. The opt-in loading cover T-288 built was removed by the owner (hosts fade their own on `onFirstDraw`), so it left no architecture; T-286's one-line test change (I-160, accepted) is not architectural.

### Good guest

Good guest (O-055, G-016; T-250 to T-258): several viewers share a page without touching it or each other.
- (1) Moon data: `moonSystem.load` fetches per request the chunks its own window, history and year-after need that are not yet held, into one shared append-only store per planet (index fetched once, in-flight dedupe per chunk), so a second scene, a rebuild or a remount of the same planet still gets its moons; a window outside a moon's years still refuses with `out-of-span`; `load` no longer returns the first call's promise.
- (2) Pictures: the page-wide picture book is gone. `BodyVisual` carries `picture` and `desktopPicture` names and `ExperienceDefinition.pictures` carries the viewer's pictures from `data` (`assembleScene`) or hand-built (the site and the planets demo, which import `PICTURES` from `astraeus-data` and hand it in) to `BodyView` (`describeBody(..., pictures)`) and `SkyView` (`pictureSet`); `installData` checks rights but registers nothing, so a viewer draws only the pictures of the packages passed to it.
- (3) Developer tools: `mount` and `AstraeusScene` take `developerTools` (default off, read at build); the shell draws the toggle and drawer only when handed that content and the drawer's code is not loaded otherwise; the Developer-placed switches and the Copy-view-link button exist only with it (`address: true` alone reads the address, no copy button).
- (4) Ids: every viewer element id is made with `useId` in the nearest owner and passed down, so aria pairs resolve within the viewer and no fixed id is left (internal `Collapsible` `id` became `fold`, `SettingGroup` `id` became `name`; tests find parts by `[data-setting-group]`, `[data-fold-toggle]`, not ids).
- (5) The engine never looks up page elements: the loading cover is the host's, handed in as the internal `claimCover` prop (`App` to `AstraeusScene` to `FrameState.cover`) and shown, faded or failed by `packages/astraeus-site/src/bootCover.ts`; `mount` and `AstraeusScene` take none. Escape and markers are scoped: `shell/viewerKeys.ts` (`VIEWER_ROOT_CLASS`, `keyIsForViewer`) makes every document key listener of the viewer act only for keys pressed inside its root or on the bare page, `useDrawers` takes the viewer root ref, and the marker layer measures panels inside its own viewer root.
- (6) Styles: every rule of `app/style.css` and `shell/style.css`, and of the bar, phone and embedded sheets, sits under the root class `.astraeus-shell`, which also carries the custom properties (`--ui-*`, `--perf-*`), `color-scheme`, the base font and the black background, so the viewer owns no page-level style (`html`, `body`, `#app`); `mount` and `AstraeusScene` make their own element a containing block (`position: relative` if static, `overflow: hidden` if visible, a set value kept) and the host sizes it; `mount`'s `unmount` restores the inline `isolation`, `position` and `overflow` the host element had. Specificity convention: where a plain `.astraeus-shell` prefix would let a class rule beat the generic `.astraeus-shell button|select|input|.ui-*` rules, the prefix is written `:where(.astraeus-shell)` to keep the old weight (31 sites, listed in the T-257 evidence); the T-257 builders' static specificity model missed one flip (I-140: an open nested fold heading went accent to muted, because it skipped a `:not()` subject), so the proof is now `packages/astraeus/tests/computedLook.test.ts`, which renders the real App in four layouts, both bundle orders and two definitions and compares every element's computed style with the checked-in `tests/fixtures/computed-look.baseline.json` (a flip fails `npm test`; an intended look change regenerates it with `npm run look:lock` and the baseline diff is reviewed). The static model is retired, and the root's own rule `main.astraeus-shell` is `.astraeus-shell:is(main)`. The isolation allowlist is empty and the CSS and id scans hold it there. Public surface unchanged apart from `developerTools`; `tests/twoViewers.test.ts` is the two-viewer suite the steps made green.

### Host-page behaviour

Host-page behaviour (O-044): `App` has an internal `writeTitle` prop (not public API) that `mount` and `AstraeusScene` set false, so the viewer never writes `document.title`; the viewer's Escape handlers yield to a `defaultPrevented` keydown; both mount routes set `isolation: isolate`. A scene with no `setTime`, timeline window or trajectory opens at the current time with a window of +/- 15 days (`TimelinePlan.span` in `api/planTimeline.ts`). On phones the story sheet forwards wheel and pinch to the scene canvas (`shell/useZoomThrough.ts`).

### Paths across the solar system

Paths across the solar system (O-046): `addTrajectory` is accepted in a Sun-centred scene (it was rejected). A tracked path's line is one relative trail (`pathRules.ts`): each sample is the position from `lineFixedTo` (any scene body; default the scene centre) at that sample's own time, then the whole line is carried to that body's place from the scene centre at the clock time (`relativeTrailKm` gains an optional `against`; `TrackedBody` gains `lineFixedTo`), so `"sun"` holds a probe's line still against the Sun and the default keeps Earth-centred paths as before. Path frame: `addTrajectory` input (samples and provider states) is EQJ about `center`, which defaults to the scene's centre (its first body; owner decision 2026-10-30; a path added before any body is rebuilt in `#register` when the first body arrives); `plane: "ecliptic-j2000"` rotates positions and velocities to EQJ once at entry with the orb adapter's existing matrix (drawing, `stateOf` and readouts read the stored EQJ trajectory); a provider state's `orientation` passes through unrotated (known limit: probes carry none). `solarSystemScale` is a public export, the same policy the viewer builds per experience; `setScale(solarSystemScale)` opens a Sun-centred scene with an enlarged body on it, else building it (`check`, `mount`) throws `bad-scale`, and such a scene offers it second in place of the readable scale. Label reach is one rule for bodies and paths (`labelReach` in `api/planBodies.ts`): none in a Sun-centred or `fitOrbit` scene, else the camera reach (at least 500); `labelReachEarthRadii` on `addBody` and `addTrajectory` replaces it for one item (Apollo 11 sets 4 on its paths). Tracked paths also report to `data-paths` (`TrackedBodyView.screenReadout`) for the browser check. A made-up probe fixture (`src/synthetic/syntheticProbeDefinition.ts`, `?experience=synthetic-probe`, dev only) is built only through the public Scene API.

### Planet positions from Horizons

Planet positions from Horizons (O-063, G-017; T-289, T-290; note `docs/architecture/planet-accuracy-o063.md`): every planet's series in `data/ephemerides/planets/planets.json` is a piecewise Chebyshev fit (as before, made by `tools/import/planet-fits.mjs`) of its system barycentre about the Sun from JPL Horizons, no longer Orb's VSOP87A: for a planet with a moon system the importer fits Horizons' planet centre (DE441 with that planet's satellite ephemeris) minus the centre's offset about its barycentre, and Mercury and Venus are their own barycentre. One binding rule, `planetBinding` / `barycentreOffsetKm` (`core/bodies/planetTrajectory.ts`, bindings listed in `core/bodies/index.ts`), adds the planet's offset from its barycentre from its moon package when that package is loaded (Pluto's old binding made general), so with the package the planet equals Horizons' planet centre (measured under 1 km from 1972; before 1972 up to about 35 km from time labels, UT1 and UTC's rubber seconds against the engine's smooth TT minus UTC) and without it the planet is the barycentre (the measured wobble, up to about 300 km at Saturn). Uranus and Neptune therefore follow their satellite-ephemeris barycentres, which differ from DE441 bodies 7 and 8 by up to 3,441 and 742 km (owner choice). One shared `planetEphemeris` provenance carries the measured figures. Earth keeps its EPV00 model (measured within 7.3 km from 1972). The engine's first download is unchanged: the planet data is a lazy chunk (348,839 B, was 432,063 B). `tests/planetAccuracyFlybys.test.ts` pins the errors against a saved Horizons fixture.

### Journeys across years

Journeys across years (O-047): a body's positions can cover their own years. A moon-fit `index.json` may give each body an optional `span`; the ephemeris answers a body inside its span, narrowed by its centre's and the time-scale table's (the set-level `span` is informational). A scene whose window leaves a loaded moon's years, or the planet series (1950 to 2045, `planetSeriesSpan()`), fails once at mount with the new `SceneError` code `out-of-span` (moons through `MoonOutOfSpanError` in `moonSystem.load`, planets in the definition's `prepare`, reached by `scene.load` and `mount`). The four planet packages hold the main moons and the planet from 1950 (the rest 2010 to 2030); the fitted-moon time-scale table before 1972 is built from daily samples while the planet series keeps Orb's polynomial, so two UTC definitions coexist there and are not reconciled (accepted limit; the importer's merge writes `span` on every body of a merged set, and a mapped moon's `validUtc` follows its own span). One orbit-line rule, by coverage and never by name: a Sun-circling body is drawn from its own source over one full turn where that is covered, else as the two-body ellipse osculating at the opening time; `fitOrbit`'s farthest distance is settled in setup (`assembleScene`, or `prepare` once the series are in), so a failure reaches the host once. `addTrajectory` takes `provenanceSpans` (resolved against the clock in `infoView` through `spanProvenanceAt`, the one lookup shared with activity windows, so objects are time-dependent like windows). The timeline takes `pacing`: pure `pacedRate` in `core/pacing.ts` (log-space smoothstep over spans and event rules; spans (zones with no event) set the cruise, laid over the base slowest last; an event rule eases from the cruise, and the paced rate is the minimum of the cruise and of each touching rule's blend, so it is continuous at every ramp edge, the slowest wins where rules' ramps meet, and the base is exact where none touches, O-069) which the viewer applies to the one clock (`SceneRuntime.pacing`, `SceneControls.paceAuto`, `ViewerState.auto`, `ViewerControl.paced`). Paced playback integrates the rate rather than reading it once per frame (O-069): pure `pacedAdvance` sub-steps the frame's real time, stopping at each zone or ramp edge and at most 1/32 of a ramp (trapezoid-timed, at most `MAX_PACE_STEPS` 4,096 sub-steps, leftover real time dropped so a hidden tab slows rather than skips); `stepPacing` moves the clock to that time through its public `seek`/`setRate` from where it last left it (`PaceView.last`), and falls back to the one-rate step on the first step, while paused, or after a move it did not make; during a view-switch ease `pacedAdvance` integrates the eased rate (the paced shape times exp(k0 (1 - weight)), k0 being the switch's own change, log start rate minus log paced rate at the switch, fixed on first use in `PaceView.ease.k0`; sub-steps also at most 1/32 of the ease's second), so a zone reached during the ease still slows playback and is entered (clock advance versus real time, 5 ms slack; `seekTo` clears `last`). The clock holds no pacing knowledge; `frameTime` (`app/sceneFrame.ts`) runs the pace step, then wrap or stop, then re-applies the paced rate after a wrap or stop, and `App`'s 100 ms playback tick calls the same `frameTime`, so zone reports follow the slow-downs at any frame rate. Host control is one seam: `app/viewerPort.ts` (the interface `App` is given as `host`) implemented by `api/viewerLink.ts` (`ViewerLink`, validation and `SceneError`s); `App` attaches `{window, rates, read, seek, setRate}` on its one clock and publishes snapshots (`playback` on the 100 ms tick, `visitor` from the timeline handlers), and `ViewerLink.rateSource` (`scene` or `chosen`) is what pacing's override and release use. The public handle gains `timeUtcMs` (`time` until O-057), `rate`, `setTime`, `setRate`, `onChange`; the speed menu shows exactly the scene's `rates` (I-106). ### The sky view

The sky view (O-064, G-018; T-291 to T-293): the camera can stand at a body's centre and look out. It is camera state only; nothing in State changes (ARCH-02).

- (4) Openings: `scene.camera.lookOut(body, { direction?, fovDeg? })` (the same direction forms as `setCamera`; an id is resolved on the first frame, see (3)) and `setStartView(sky pose)`; the last opening call wins.

### Constellations

Constellations (O-067, G-018; T-303 to T-306): the 88 IAU constellations are data in the optional package `astraeus-data-constellations`, never in the engine (the engine knows no constellation, ARCH-01).
- (1) Sources (owner choices recorded in `docs/architecture/constellations-o067.md`): figures from Stellarium's `modern_iau` sky culture (the IAU's figures as drawn by Sky & Telescope, typed in by the Stellarium team, CC BY-SA 4.0), boundaries from Stellarium's Delporte
- (1930) corner points at B1875 (CC BY-SA 4.0), names from the IAU table (CC BY 4.0); each pinned by commit and SHA-256 in `provenance.json`; share-alike applies to the two data files and their adaptations, not to the code (MIT).
- (2) Import (`tools/import/constellations.mjs`, in the package like the other importers): zero-length and repeated figure steps are dropped; xi Ursae Majoris (HIP 55203) is a position end because the engine's star list holds it without a Hipparcos number; boundary edges are chained into closed rings, points added at most 1 degree apart (tighter near a pole) and precessed B1875 to J2000 (not read from the RA-sorted `bound_20.dat`), then cross-checked against CDS VI/49 (0.01 degree tolerance; the run fails above it). Serpens has two outlines (Caput, Cauda) because a `SkyFigureInput` boundary holds one ring.
- (3) Shapes: `figures.json` `abbr -> [[end, end], ...]`, `boundaries.json` `abbr -> [flat [ra, dec, ...], ...]`, `names.json` `abbr -> {name, english, genitive}`; about 66 kB packed, 200 kB unpacked, 10 files.
- (4) Helper: `constellations(which | "all", { outlines, shown, color, labelColor, listed, idPrefix })` is async (the data load as chunks) and returns `SkyFigureInput[]` for `scene.addSkyFigures`, importing only public `astraeus` types (a data package may hand back engine input through a helper without a deep import); ids are the abbreviation, `<abbr>-boundary` and `Ser-boundary-1`/`-2`; unknown or repeated abbreviations throw `RangeError`; it loads the outline file only when `outlines` is true; cards carry illustrative provenance and no facts (a story app adds those). A Node app can place star-end figures: the star list is read by the same bundled-file reader as the moon chunks (`core/readBytes.ts`: `file:` through `node:fs`, else `fetch`; I-167), and the all-88 test no longer stubs `fetch`.
- (5) Example: `examples/hello-sky` (see the map) is the proof that a plain app needs only `mount`, the helper and story steps; its first download is stated in its README.

## Decisions

### Public API shape (G-016, owner 2026-11-01)

The owner's principles for the public API, from the [api review](../docs/architecture/api-review-2026-11-01.md). Durable rules with IDs are in Guardrails (API-01 to API-07); these are how the API is shaped. Where today's code differs, G-016's Objectives (O-053, O-058, O-054, O-055, O-056, O-059, O-057, in that order) bring it in line and this section is reconciled as they land.

- **What the product is (D1).** A scene builder, a full viewer (`mount` and `AstraeusScene`) and numbers without a viewer (`stateOf`, `provenanceOf` after one public load). No viewer-free entry point and no public 3D parts until a real user needs them.
- **Verb grammar.** `add*` appends and a repeated id throws `duplicate-id`; `set*` replaces the whole setting; `on*` subscribes and returns a stop function; reads are plain properties.
- **Lifecycle.** Build faults throw at `mount`; load faults reject `ready`; `ready` always settles (usable or rejected, never left pending); after `unmount` handle calls throw `not-mounted` and callbacks stop (listener registration never throws); a listener that throws does not stop the others (`api/listeners.ts`); a mounted `Scene` is frozen and later edits throw `scene-mounted`. Built in O-054; React and plain apps get the same `ViewerHandle`.
- **The engine signals, the host decides.** The engine reports what changed and offers setters but builds in no app behaviour; each signal stands alone, never only as a side effect of another feature (event zones independent of pacing, D4).
- **Numbers work without a viewer.** A Node or server app awaits one public call and can then ask about any body, moons included.
- **Use the front door ourselves.** In-repo demos and the site use only the public API; existing deep imports sit on a per-package allowlist that may only shrink, and G-016 empties it: the planets demo and the site moved onto the public API in O-059 (D6 brought forward by the owner); every demo's and the site's `src` is on the front door; the Planets demo and the site count 0 deep imports (tests and tools included), while Apollo (129) and Showers (65) keep only tests and tools that reach engine internals.
- **Compatibility.** Renames in 0.8.0 are a clean break with no aliases, listed in one CHANGELOG migration table (D2 revised by the owner: only two outside apps exist, so break and rework them now); `toDefinition` is removed in 0.8.0 with public replacements (D10), and `src/api/definitionOf.ts` is the one internal route to a scene's assembly; groups must state their `plane` (D3); several viewers per page are supported (D9); the Developer drawer is hidden unless a host asks (D8); the React peer covers all of React 19 (D7).
- **Names and shapes as built (O-057, T-274 to T-280).** Spans bind inputs only (owner, 2026-11-07): what a caller gives is `{ start, end }`, and what the engine reports stays flat unit-named numbers such as `windowStartUtcMs`, so the reported time is `timeUtcMs` on `ViewerHandle`, `ViewerChange` and `EventZoneChange`. Every renamed input is one row of `RENAMED_INPUTS` (`api/renamedInputs.ts`), read by `rejectRenamed` in each receiving call, so a plain JavaScript caller gets `renamed` naming the replacement; no alias code exists, and `core/elementsBody.ts` refuses the same record names with `bad-element` for callers of the parser. `Scene` keeps its assembly internal: `api/definitionOf.ts` (a WeakMap filled by the `Scene` constructor) is the one route for `mount`, `load`, `check` and tests, is not exported from the root, and reaches other packages' tests as `astraeus/tests/definitionOf`. `SceneCamera` is a type-only export and `RateSource` is internal. Story panels are typed `StoryPanelInput`s: `checkStoryPanel` and `checkPanelPlayback` (`core/storyPanels.ts`) check shape at the call, `resolveStoryPanels` resolves links when the scene is built, `provenance` replaces `badge` and `sources`, and `setStoryPanelPlayback` holds `pauseSeconds` and `autoOpen`. `TimeInput` and `timeInputMs` live in `core/timeInput.ts`, re-exported by `api/time.ts`, so `core/` can convert a moment without importing `api/` (ARCH-04). `add*` appends and a repeated id throws `duplicate-id` on every add call, `addEvents` included (I-145). The catalogue holds the Sun, planets, dwarf planets and moons only (`assets.test.ts` fails on anything else); a comet is demo data through `addBodyFromElements`, and a whole orbit line comes only from the body's own source or its record's sampling (`BUILT_IN_SAMPLING` is gone).
