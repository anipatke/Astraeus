# Astraeus — Design

## Architecture

Astraeus is a TypeScript astronomy engine with a scientific core, a reusable asset layer, React Three Fiber presentation and a generic viewer shell. The site and demos live in separate packages. Absolute UTC feeds physical state in EQJ kilometres; scale policies, floating origin and render-axis conversion act downstream and never change scientific State. The engine imports no other workspace package. Guardrails owns the layer, naming, provenance and reuse constraints.

This overview describes current architecture. Detailed contracts and dated reconciliation records are linked below; load only the relevant sections. Planned work belongs in Objectives, verification results in Tasks and Checks, and original owner intent in Idea.

## Interfaces and Data Flow

`Scene` is the public story-building API. `prepareScene` converts it to the existing `ExperienceDefinition` and loads its data; both `mount` and the exported React `AstraeusScene` use that path. React 19, React DOM, Fiber and Three.js are published peer dependencies. The API reference is generated from `src/api/index.ts` exports and their doc comments; missing export documentation is tested.

Scene and host-link split (O-058, no behaviour change; `tests/scenePin.test.ts` pins the scene output): `Scene` holds one plan per concern (paths, bodies, groups and activities, story, timeline, views, camera) and `assembleScene` joins them into the `ExperienceDefinition`; a plan never imports the `Scene` and takes the ids it needs as callbacks, with type-only imports of the public input types from `scene.ts` (accepted type-only cycle). The host link keeps one public `ViewerLink` split by concern (clock, views, camera, zones) over a shared accessor. The two parsers the API reads (story panels, start view) live in `core/` so `api/` stops importing display code; `tests/apiImports.test.ts` limits the remaining `api/` imports of `shell/` and `app/` to a reasoned allowlist, and `tools/api-rules.mjs` covers story panels through the type walk (its parser-reading special case went in O-057 T-278). The demos' deep imports of the old `shell/storyPanels` and `app/viewLink` paths keep working through the re-exports until O-059 moves them onto the public API.

One handle, one lifecycle (O-054, G-016; T-240 to T-249): `ViewerHandle` (`api/viewerHandle.ts`, exported type) holds every read, setter and signal; `MountedScene` is `ViewerHandle` plus `ready` and `unmount`. `viewerHandleOf(link)` is the only builder of the handle: `mount` makes one per call and `AstraeusScene` one per component life (given through the React 19 `ref` prop and `onReady(handle)`, the same object across a rebuild with a new `scene`), so the two embedding paths cannot drift; `tests/lifecycle.test.ts` runs one suite against both. Errors: before `ready` or after `unmount` every read is undefined and every call throws the new code `not-mounted` (`missing-data` now means only missing data packages); listener registration (`onChange`, `onEventZone`, `onSelect`, `onCameraChange`) is exempt, never throws at any time and delivers nothing after `unmount`. `ViewerLink.whenAttached()` rejects with `not-mounted` when `close()` comes before the attach (so `ready` always settles); `ViewerLink.reopen()` takes a closed link back into use for a host effect that was cleaned up and replayed (React StrictMode) before the viewer drew, while a real unmount leaves it closed. The React driver in `lifecycle.test.ts` commits through `flushSync`, which fixed the T-243 StrictMode flake (30 of 30 runs); it is test-only, not architecture. The same T-240 error rule is reflected: a repeated `addActivity` id is `duplicate-id`, a data package whose moon positions name a planet without a moon system is `bad-data` (new code), and the two internal range faults of the sun-orbit code are named error classes in `core/`. Listeners: `api/listeners.ts` is the one helper that calls a set of listeners so a throwing one is reported (`reportError`, else rethrown on a timer) after the others have run; the clock, zone, selection and camera parts all use it. Scene freeze: `prepareScene` marks the scene in a module `WeakSet` (`api/sceneFreeze.ts`, so the public surface gains nothing) and every mutator of `Scene` and `SceneCamera` throws `scene-mounted`; reads (`stateOf`, `provenanceOf`, the scene reads, camera getters) still answer, a scene may be mounted again, and a failed build leaves it editable. Host signals (each a separate part of `ViewerLink`, none of it State, ARCH-02): `ViewerControl` gains required `playable` and `setPlaying` (`viewerPort.ts`; the handle's `playing`/`setPlaying` go through the visitor's own play handler, one clock, `bad-timeline` without a play control); `ViewerState` gains optional `selected` and the link has a fifth part `viewerSelection.ts` (`selected`, `onSelect`, `SelectionChange {object?, timeUtcMs, cause}`; the field is `timeUtcMs` per API-04, as `ViewerChange.timeUtcMs` also is since O-057; a selection dropped because time or the view moved takes the cause of whatever last moved them: `ViewerLink` keeps the cause of the last published clock/view change, and every shell selection path names its origin, a required `SelectionOrigin` argument of `onSelectionChange` (`"visitor"` for the menu, a pick, a preset or a marker; `"move"` for the fallback drop and a view rule's framing target, so a new path cannot omit it), so `onSelect` agrees with `onChange` (`host` for `setTime`/`setRate`/`setPlaying`/`setView`, `playback` for the clock running, `visitor` for the visitor's own moves; I-137); there is no separate selection-cause flag); `ViewerCamera` is stateful (last reported pose, report time, listeners) and is the fourth part `publish` calls (clock, zones, selection, camera), so `onCameraChange` rides the existing 100 ms viewer publish with no new frame-loop work and reports a pose only when it differs, at most about ten times a second. Unawaited `ready` (owner decision, 2026-11-01, "Only hide the expected 'taken down early' case"): `mount` marks `ready` handled only when it rejects with `SceneError` `not-mounted` (an early `unmount`), so a host that never awaits it gets no unhandled rejection for that; any other rejection, such as a failed load, stays unhandled until someone awaits `ready`, as before. Allowlist growth is judged per finding (Decisions, "Allowlist growth counted per finding").

Good guest (O-055, G-016; T-250 to T-258): several viewers share a page without touching it or each other. (1) Moon data: `moonSystem.load` fetches per request the chunks its own window, history and year-after need that are not yet held, into one shared append-only store per planet (index fetched once, in-flight dedupe per chunk), so a second scene, a rebuild or a remount of the same planet still gets its moons; a window outside a moon's years still refuses with `out-of-span`; `load` no longer returns the first call's promise. (2) Pictures: the page-wide picture book is gone. `BodyVisual` carries `picture` and `desktopPicture` names and `ExperienceDefinition.pictures` carries the viewer's pictures from `data` (`assembleScene`) or hand-built (the site and the planets demo, which import `PICTURES` from `astraeus-data` and hand it in) to `BodyView` (`describeBody(..., pictures)`) and `SkyView` (`pictureSet`); `installData` checks rights but registers nothing, so a viewer draws only the pictures of the packages passed to it. (3) Developer tools: `mount` and `AstraeusScene` take `developerTools` (default off, read at build); the shell draws the toggle and drawer only when handed that content and the drawer's code is not loaded otherwise; the Developer-placed switches and the Copy-view-link button exist only with it (`address: true` alone reads the address, no copy button). (4) Ids: every viewer element id is made with `useId` in the nearest owner and passed down, so aria pairs resolve within the viewer and no fixed id is left (internal `Collapsible` `id` became `fold`, `SettingGroup` `id` became `name`; tests find parts by `[data-setting-group]`, `[data-fold-toggle]`, not ids). (5) The engine never looks up page elements: the loading cover is the host's, handed in as the internal `claimCover` prop (`App` to `AstraeusScene` to `FrameState.cover`) and shown, faded or failed by `packages/astraeus-site/src/bootCover.ts`; `mount` and `AstraeusScene` take none. Escape and markers are scoped: `shell/viewerKeys.ts` (`VIEWER_ROOT_CLASS`, `keyIsForViewer`) makes every document key listener of the viewer act only for keys pressed inside its root or on the bare page, `useDrawers` takes the viewer root ref, and the marker layer measures panels inside its own viewer root. (6) Styles: every rule of `app/style.css` and `shell/style.css`, and of the bar, phone and embedded sheets, sits under the root class `.astraeus-shell`, which also carries the custom properties (`--ui-*`, `--perf-*`), `color-scheme`, the base font and the black background, so the viewer owns no page-level style (`html`, `body`, `#app`); `mount` and `AstraeusScene` make their own element a containing block (`position: relative` if static, `overflow: hidden` if visible, a set value kept) and the host sizes it; `mount`'s `unmount` restores the inline `isolation`, `position` and `overflow` the host element had. Specificity convention: where a plain `.astraeus-shell` prefix would let a class rule beat the generic `.astraeus-shell button|select|input|.ui-*` rules, the prefix is written `:where(.astraeus-shell)` to keep the old weight (31 sites, listed in the T-257 evidence); the T-257 builders' static specificity model missed one flip (I-140: an open nested fold heading went accent to muted, because it skipped a `:not()` subject), so the proof is now `packages/astraeus/tests/computedLook.test.ts`, which renders the real App in four layouts, both bundle orders and two definitions and compares every element's computed style with the checked-in `tests/fixtures/computed-look.baseline.json` (a flip fails `npm test`; an intended look change regenerates it with `npm run look:lock` and the baseline diff is reviewed). The static model is retired, and the root's own rule `main.astraeus-shell` is `.astraeus-shell:is(main)`. The isolation allowlist is empty and the CSS and id scans hold it there. Public surface unchanged apart from `developerTools`; `tests/twoViewers.test.ts` is the two-viewer suite the steps made green.

Host-page behaviour (O-044): `App` has an internal `writeTitle` prop (not public API) that `mount` and `AstraeusScene` set false, so the viewer never writes `document.title`; the viewer's Escape handlers yield to a `defaultPrevented` keydown; both mount routes set `isolation: isolate`. A scene with no `setTime`, timeline window or trajectory opens at the current time with a window of +/- 15 days (`TimelinePlan.span` in `api/planTimeline.ts`). On phones the story sheet forwards wheel and pinch to the scene canvas (`shell/useZoomThrough.ts`).

Paths across the solar system (O-046): `addTrajectory` is accepted in a Sun-centred scene (it was rejected). A tracked path's line is one relative trail (`pathRules.ts`): each sample is the position from `lineFixedTo` (any scene body; default the scene centre) at that sample's own time, then the whole line is carried to that body's place from the scene centre at the clock time (`relativeTrailKm` gains an optional `against`; `TrackedBody` gains `lineFixedTo`), so `"sun"` holds a probe's line still against the Sun and the default keeps Earth-centred paths as before. Path frame: `addTrajectory` input (samples and provider states) is EQJ about `center`, which defaults to the scene's centre (its first body; owner decision 2026-10-30; a path added before any body is rebuilt in `#register` when the first body arrives); `plane: "ecliptic-j2000"` rotates positions and velocities to EQJ once at entry with the orb adapter's existing matrix (drawing, `stateOf` and readouts read the stored EQJ trajectory); a provider state's `orientation` passes through unrotated (known limit: probes carry none). `solarSystemScale` is a public export, the same policy the viewer builds per experience; `setScale(solarSystemScale)` opens a Sun-centred scene with an enlarged body on it, else building it (`check`, `mount`) throws `bad-scale`, and such a scene offers it second in place of the readable scale. Label reach is one rule for bodies and paths (`labelReach` in `api/planBodies.ts`): none in a Sun-centred or `fitOrbit` scene, else the camera reach (at least 500); `labelReachEarthRadii` on `addBody` and `addTrajectory` replaces it for one item (Apollo 11 sets 4 on its paths). Tracked paths also report to `data-paths` (`TrackedBodyView.screenReadout`) for the browser check. A made-up probe fixture (`src/synthetic/syntheticProbeDefinition.ts`, `?experience=synthetic-probe`, dev only) is built only through the public Scene API.

Journeys across years (O-047): a body's positions can cover their own years. A moon-fit `index.json` may give each body an optional `span`; the ephemeris answers a body inside its span, narrowed by its centre's and the time-scale table's (the set-level `span` is informational). A scene whose window leaves a loaded moon's years, or the planet series (1950 to 2045, `planetSeriesSpan()`), fails once at mount with the new `SceneError` code `out-of-span` (moons through `MoonOutOfSpanError` in `moonSystem.load`, planets in the definition's `prepare`, reached by `scene.load` and `mount`). The four planet packages hold the main moons and the planet from 1950 (the rest 2010 to 2030); the fitted-moon time-scale table before 1972 is built from daily samples while the planet series keeps Orb's polynomial, so two UTC definitions coexist there and are not reconciled (accepted limit; the importer's merge writes `span` on every body of a merged set, and a mapped moon's `validUtc` follows its own span). One orbit-line rule, by coverage and never by name: a Sun-circling body is drawn from its own source over one full turn where that is covered, else as the two-body ellipse osculating at the opening time; `fitOrbit`'s farthest distance is settled in setup (`assembleScene`, or `prepare` once the series are in), so a failure reaches the host once. `addTrajectory` takes `provenanceSpans` (resolved against the clock in `infoView` through `spanProvenanceAt`, the one lookup shared with activity windows, so objects are time-dependent like windows). The timeline takes `pacing`: pure `pacedRate` in `core/pacing.ts` (log-space smoothstep over spans and event rules) which the viewer applies to the one clock (`SceneRuntime.pacing`, `SceneControls.paceAuto`, `ViewerState.auto`, `ViewerControl.paced`). Host control is one seam: `app/viewerPort.ts` (the interface `App` is given as `host`) implemented by `api/viewerLink.ts` (`ViewerLink`, validation and `SceneError`s); `App` attaches `{window, rates, read, seek, setRate}` on its one clock and publishes snapshots (`playback` on the 100 ms tick, `visitor` from the timeline handlers), and `ViewerLink.rateSource` (`scene` or `chosen`) is what pacing's override and release use. The public handle gains `timeUtcMs` (`time` until O-057), `rate`, `setTime`, `setRate`, `onChange`; the speed menu shows exactly the scene's `rates` (I-106). Zoom-out (I-114): `CameraReach` gains `cover` (declared by `assembleScene` in a Sun-centred scene that has paths about its centre and no `setReach` or `fitOrbit`): twice the paths' farthest distance, which `liveReach` turns into a widen-only default zoom-out and a far plane of 2.5 times it for the live canvas shape (never narrowing the default, and a declared reach wins), so a path to 170 AU frames whole from any point on it. Playback in a scene with a timeline bar that does not loop stops on the window's edge (`SimulationClock.stopWithin`, the counterpart of `wrapWithin`; `SceneRuntime.stopAtWindow`), because positions past the loaded window were requested every frame once the clock ran on. The made-up `synthetic-journey` fixture (`src/synthetic/syntheticJourneyScene.ts`, site `?experience=synthetic-journey`, dev only; its moon chunks come from `packages/astraeus-site/src/journeyData.ts`) proves it on the public Scene API with no mission data.

Near planets and rings (O-048): the renderer uses a logarithmic depth buffer (`Canvas gl.logarithmicDepthBuffer`), so a planet at the camera stays drawn when the far plane reaches a 170 AU path (I-117); every custom `ShaderMaterial` in `src/app` carries the log-depth chunks (SkyView is exempt: depth test and write off), guarded by `tests/logDepth.test.ts`, and the canvas reports `data-depth-mode` for the browser checks. Rings are catalogue data: Jupiter, Saturn, Uranus and Neptune carry `BodyVisual.rings` in their one definition (ring data in `core/bodies/outerPlanetRingData.ts`, apart from the moon lists to keep the first download small), not an experience opt-in (I-118). `CelestialBodyDefinition` gains optional `orbitPeriodDays` (the moon's sidereal period about its parent, read once from its record by `core/siderealPeriod.ts`) and `orbitLineFades`; the scene's orbit-line rule (`moonOrbitPath`) draws any catalogued moon with a period, and a moon without one (Phobos, Deimos) throws `no-orbit` at `addBody` (I-119). `OrbitSetView` (the body-set layer for demos) is not reused: it samples a set's own sources with a per-frame osculating period, while the composition path takes one static span, so the two stay separate. `TimelineEvent` gains optional `object`; the scene's build refuses an object the scene lacks (`bad-event`) and the shell's Go to, Previous and Next frame it with the existing Focus preset (I-120; no State change). Label layout keeps one bit of memory per label (shown or hidden by overlap) with a 14 px re-appear margin over the 6 px padding, so crossing labels swap once (I-121; layout only, ARCH-02). The astraeus pack has no file-count limit (owner, O-051 T-218): `tools/check-packs.mjs` fails a packed file that is not a real source module or a file `package.json` `x-publish.files` lists (`strayFiles`); size limits stay.
One path through every stretch (O-050): `addTrajectory`'s `lineFixedTo` is `BodyId | { start, end, body }[] | "auto"`; `TrackedBody.lineFixedTo` holds `string | LineStretch[]` (ms), and `TrackedBodyView` draws the relative trail per stretch (`lineAgainstAt`, `lineBodies` in `app/mission.ts`). A stretch's boundary sample belongs to the later stretch, and time outside every stretch is drawn against the scene centre. `api/pathProvenance.ts` holds one span planner (`planSpans`) behind `planPathProvenance` and `planLineStretches`; `State` and `stateOf` are untouched. `"auto"` is a reserved value resolved by the pure `api/sphereOfInfluence.ts` in `assembleScene` (or `prepare` when the planet series load late, which replaces the `trackedBodies` entry) into the same list the explicit form takes, so the menu, drawing and follow share one path: each sample is fixed to the innermost scene body whose Laplace sphere of influence `a (m / M)^(2/5)` holds it, the root body holds everything, and a body with no GM is skipped (listed moons added by id have none; Pluto and Charon and the main moons do). Timeline markers (events, story panels, window peaks) are laid out by `groupMarkers` in `shell/timelineModel.ts`: markers closer than `MARKER_MIN_SPACING_PX` (22 px) on the measured track gather into one numbered mark at their mean position whose list opens above the track with each member a full-size button doing what its own marker does; an unmeasured track gathers nothing, and Previous/Next still step every event. The packed package is proved by `check:node-consumer` (listed, `"auto"` and Moon-orbit paths, one menu object each) and by the synthetic journey (`?experience=synthetic-journey`, dev only), whose traveller is drawn against the Sun, Jupiter for 20 days either side of its pass, then the Sun, with Io, Europa and Ganymede passes within nine hours of Jupiter's gathered under one mark; the browser smoke follows the camera across both boundaries and presses each gathered member at 1280x720 and 375x667.

Every listed moon addable (O-049, I-122): the moon lists (458 moons) each carry `orbitPeriodDays` (JPL Planetary Satellite Mean Elements, sidereal P; `tools/import/moon-periods.mjs`, transcribed to `planet-moon-periods.json`). A generated slim lookup `core/bodies/listedMoons.ts` (id, label, mean radius, period, parent, data package `astraeus-data-<parent>`, fit-set body, and an `early` flag for moons whose fits start in 1950, read from the data packages' indexes) is what `addBody` consults, so the full lists stay out of the first download (+19.6 kB raw / +7.6 kB gzip in all). `addBody(id)` for a listed moon the built-in catalogue lacks goes through one rule (`core/bodies/listedMoonBodies.ts`, `assets/bodies/listedMoons.ts`): a grey sphere at the JPL mean radius (the picture pack's picture when registered under the id), positioned by its planet's moon system binding, requiring the planet's data package. The definition and binding extend the scene's own catalogue (`assets/catalogue.extendCatalogueWithMoons`), never the global one; `assembleScene` passes `catalogue` whenever it differs from the built-in one (before: elements bodies only) and `installData` takes it; `MOON_SYSTEMS` moved from `api/data.ts` to `listedMoonBodies.ts`; `MoonSystem.position`/`worstM` is optional (no engine-held worst figure for a listed moon). Public `listedMoons(planet?)` returns the refs with `requires`; `unknown-body` names it. Detailed moons keep their own catalogue definitions and periods; JPL's P for Io and Europa is shorter than the rotation-rate period by 0.36% and 0.73% (apsis not corrected), which does not reach them because they are in the built-in catalogue first, and any later use of the table period for a Jovian moon needs the apsis-corrected rule. T-212 adds Uranus's five main moons (by id, `{ orbit: true }`) and a made-up Uranus pass on 24 January 1986 to the synthetic journey (a scene change, not an architecture change).

## Decisions

### Public API shape (G-016, owner 2026-11-01)

The owner's principles for the public API, from the [api review](../docs/architecture/api-review-2026-11-01.md). Durable rules with IDs are in Guardrails (API-01 to API-07); these are how the API is shaped. Where today's code differs, G-016's Objectives (O-053, O-058, O-054, O-055, O-056, O-059, O-057, in that order) bring it in line and this section is reconciled as they land.

- **What the product is (D1).** A scene builder, a full viewer (`mount` and `AstraeusScene`) and numbers without a viewer (`stateOf`, `provenanceOf` after one public load). No viewer-free entry point and no public 3D parts until a real user needs them.
- **Verb grammar.** `add*` appends and a repeated id throws `duplicate-id`; `set*` replaces the whole setting; `on*` subscribes and returns a stop function; reads are plain properties.
- **Lifecycle.** Build faults throw at `mount`; load faults reject `ready`; `ready` always settles (usable or rejected, never left pending); after `unmount` handle calls throw `not-mounted` and callbacks stop (listener registration never throws); a listener that throws does not stop the others (`api/listeners.ts`); a mounted `Scene` is frozen and later edits throw `scene-mounted`. Built in O-054; React and plain apps get the same `ViewerHandle`.
- **The engine signals, the host decides.** The engine reports what changed and offers setters but builds in no app behaviour; each signal stands alone, never only as a side effect of another feature (event zones independent of pacing, D4).
- **Numbers work without a viewer.** A Node or server app awaits one public call and can then ask about any body, moons included.
- **Use the front door ourselves.** In-repo demos and the site use only the public API; existing deep imports sit on a per-package allowlist that may only shrink, and G-016 empties it: the planets demo and the site moved onto the public API in O-059 (D6 brought forward by the owner); every demo's and the site's `src` is on the front door; the Planets demo and the site count 0 deep imports (tests and tools included), while Apollo (129) and Showers (65) keep only tests and tools that reach engine internals.
- **Compatibility.** Renames in 0.8.0 are a clean break with no aliases, listed in one CHANGELOG migration table (D2 revised by the owner: only two outside apps exist, so break and rework them now); `toDefinition` is removed in 0.8.0 with public replacements (D10), and `src/api/definitionOf.ts` is the one internal route to a scene's assembly; groups must state their `plane` (D3); several viewers per page are supported (D9); the Developer drawer is hidden unless a host asks (D8); the React peer covers all of React 19 (D7).
- **Names and shapes as built (O-057, T-274 to T-280).** Spans bind inputs only (owner, 2026-11-07): what a caller gives is `{ start, end }`, and what the engine reports stays flat unit-named numbers such as `windowStartUtcMs`, so the reported time is `timeUtcMs` on `ViewerHandle`, `ViewerChange` and `EventZoneChange`. Every renamed input is one row of `RENAMED_INPUTS` (`api/renamedInputs.ts`), read by `rejectRenamed` in each receiving call, so a plain JavaScript caller gets `renamed` naming the replacement; no alias code exists, and `core/elementsBody.ts` refuses the same record names with `bad-element` for callers of the parser. `Scene` keeps its assembly internal: `api/definitionOf.ts` (a WeakMap filled by the `Scene` constructor) is the one route for `mount`, `load`, `check` and tests, is not exported from the root, and reaches other packages' tests as `astraeus/tests/definitionOf`. `SceneCamera` is a type-only export and `RateSource` is internal. Story panels are typed `StoryPanelInput`s: `checkStoryPanel` and `checkPanelPlayback` (`core/storyPanels.ts`) check shape at the call, `resolveStoryPanels` resolves links when the scene is built, `provenance` replaces `badge` and `sources`, and `setStoryPanelPlayback` holds `pauseSeconds` and `autoOpen`. `TimeInput` and `timeInputMs` live in `core/timeInput.ts`, re-exported by `api/time.ts`, so `core/` can convert a moment without importing `api/` (ARCH-04). `add*` appends and a repeated id throws `duplicate-id` on every add call, `addEvents` included (I-145). The catalogue holds the Sun, planets, dwarf planets and moons only (`assets.test.ts` fails on anything else); a comet is demo data through `addBodyFromElements`, and a whole orbit line comes only from the body's own source or its record's sampling (`BUILT_IN_SAMPLING` is gone).

The engine and data packages are built for npm; examples consume packed tarballs rather than workspace links. Apollo, Showers, the Planets demo and the site have been rebuilt on the public API (O-059; every `src` on the front door). The API reference is generated as a static site page.
