# Astraeus — Design

## Architecture

Astraeus is a TypeScript astronomy engine with a scientific core, a reusable asset layer, React Three Fiber presentation and a generic viewer shell. The site and demos live in separate packages. Absolute UTC feeds physical state in EQJ kilometres; scale policies, floating origin and render-axis conversion act downstream and never change scientific State. The engine imports no other workspace package. Guardrails owns the layer, naming, provenance and reuse constraints.

This overview describes current architecture. Detailed contracts and dated reconciliation records are linked below; load only the relevant sections. Planned work belongs in Objectives, verification results in Tasks and Checks, and original owner intent in Idea.

## Interfaces and Data Flow

`Scene` is the public story-building API. `prepareScene` converts it to the existing `ExperienceDefinition` and loads its data; both `mount` and the exported React `AstraeusScene` use that path. React 19, React DOM, Fiber and Three.js are published peer dependencies. The API reference is generated from `src/api/index.ts` exports and their doc comments; missing export documentation is tested.

Host-page behaviour (O-044): `App` has an internal `writeTitle` prop (not public API) that `mount` and `AstraeusScene` set false, so the viewer never writes `document.title`; the viewer's Escape handlers yield to a `defaultPrevented` keydown; both mount routes set `isolation: isolate`. A scene with no `setTime`, timeline window or trajectory opens at the current time with a window of +/- 15 days (`spanOf` in `api/scene.ts`). On phones the story sheet forwards wheel and pinch to the scene canvas (`shell/useZoomThrough.ts`).

Paths across the solar system (O-046): `addTrajectory` is accepted in a Sun-centred scene (it was rejected). A tracked path's line is one relative trail (`pathRules.ts`): each sample is the position from `lineFixedTo` (any scene body; default the scene centre) at that sample's own time, then the whole line is carried to that body's place from the scene centre at the clock time (`relativeTrailKm` gains an optional `against`; `TrackedBody` gains `lineFixedTo`), so `"sun"` holds a probe's line still against the Sun and the default keeps Earth-centred paths as before. Path frame: `addTrajectory` input (samples and provider states) is EQJ about `center`, which defaults to the scene's centre (its first body; owner decision 2026-10-30; a path added before any body is rebuilt in `#register` when the first body arrives); `plane: "ecliptic-j2000"` rotates positions and velocities to EQJ once at entry with the orb adapter's existing matrix (drawing, `stateOf` and readouts read the stored EQJ trajectory); a provider state's `orientation` passes through unrotated (known limit: probes carry none). `solarSystemScale` is a public export, the same policy the viewer builds per experience; `setScale(solarSystemScale)` opens a Sun-centred scene with an enlarged body on it, else `toDefinition` throws `bad-scale`, and such a scene offers it second in place of the readable scale. Label reach is one rule for bodies and paths (`#labelReach` in `api/scene.ts`): none in a Sun-centred or `fitOrbit` scene, else the camera reach (at least 500); `labelReach` on `addBody` and `addTrajectory` replaces it for one item (Apollo 11 sets 4 on its paths). Tracked paths also report to `data-paths` (`TrackedBodyView.screenReadout`) for the browser check. A made-up probe fixture (`src/synthetic/syntheticProbeDefinition.ts`, `?experience=synthetic-probe`, dev only) is built only through the public Scene API.

Journeys across years (O-047): a body's positions can cover their own years. A moon-fit `index.json` may give each body an optional `span`; the ephemeris answers a body inside its span, narrowed by its centre's and the time-scale table's (the set-level `span` is informational). A scene whose window leaves a loaded moon's years, or the planet series (1950 to 2045, `planetSeriesSpan()`), fails once at mount with the new `SceneError` code `out-of-span` (moons through `MoonOutOfSpanError` in `moonSystem.load`, planets in `toDefinition().prepare`). The four planet packages hold the main moons and the planet from 1950 (the rest 2010 to 2030); the fitted-moon time-scale table before 1972 is built from daily samples while the planet series keeps Orb's polynomial, so two UTC definitions coexist there and are not reconciled (accepted limit; the importer's merge writes `span` on every body of a merged set, and a mapped moon's `validUtc` follows its own span). One orbit-line rule, by coverage and never by name: a Sun-circling body is drawn from its own source over one full turn where that is covered, else as the two-body ellipse osculating at the opening time; `fitOrbit`'s farthest distance is settled in setup (`toDefinition`, or `prepare` once the series are in), so a failure reaches the host once. `addTrajectory` takes `provenanceSpans` (resolved against the clock in `infoView` through `spanProvenanceAt`, the one lookup shared with activity windows, so objects are time-dependent like windows). The timeline takes `pacing`: pure `pacedRate` in `core/pacing.ts` (log-space smoothstep over spans and event rules) which the viewer applies to the one clock (`SceneRuntime.pacing`, `SceneControls.paceAuto`, `ViewerState.auto`, `ViewerControl.paced`). Host control is one seam: `app/viewerPort.ts` (the interface `App` is given as `host`) implemented by `api/viewerLink.ts` (`ViewerLink`, validation and `SceneError`s); `App` attaches `{window, rates, read, seek, setRate}` on its one clock and publishes snapshots (`playback` on the 100 ms tick, `visitor` from the timeline handlers), and `ViewerLink.rateSource` (`scene` or `chosen`) is what pacing's override and release use. The public handle gains `time`, `rate`, `setTime`, `setRate`, `onChange`; the speed menu shows exactly the scene's `rates` (I-106). Zoom-out (I-114): `CameraReach` gains `cover` (declared by `toDefinition` in a Sun-centred scene that has paths about its centre and no `setReach` or `fitOrbit`): twice the paths' farthest distance, which `liveReach` turns into a widen-only default zoom-out and a far plane of 2.5 times it for the live canvas shape (never narrowing the default, and a declared reach wins), so a path to 170 AU frames whole from any point on it. Playback in a scene with a timeline bar that does not loop stops on the window's edge (`SimulationClock.stopWithin`, the counterpart of `wrapWithin`; `SceneRuntime.stopAtWindow`), because positions past the loaded window were requested every frame once the clock ran on. The made-up `synthetic-journey` fixture (`src/synthetic/syntheticJourneyScene.ts`, site `?experience=synthetic-journey`, dev only; its moon chunks come from `packages/astraeus-site/src/journeyData.ts`) proves it on the public Scene API with no mission data.

Near planets and rings (O-048): the renderer uses a logarithmic depth buffer (`Canvas gl.logarithmicDepthBuffer`), so a planet at the camera stays drawn when the far plane reaches a 170 AU path (I-117); every custom `ShaderMaterial` in `src/app` carries the log-depth chunks (SkyView is exempt: depth test and write off), guarded by `tests/logDepth.test.ts`, and the canvas reports `data-depth-mode` for the browser checks. Rings are catalogue data: Jupiter, Saturn, Uranus and Neptune carry `BodyVisual.rings` in their one definition (ring data in `core/bodies/outerPlanetRingData.ts`, apart from the moon lists to keep the first download small), not an experience opt-in (I-118). `CelestialBodyDefinition` gains optional `orbitPeriodDays` (the moon's sidereal period about its parent, read once from its record by `core/siderealPeriod.ts`) and `orbitLineFades`; the scene's orbit-line rule (`moonOrbitPath`) draws any catalogued moon with a period, and a moon without one (Phobos, Deimos) throws `no-orbit` at `addBody` (I-119). `OrbitSetView` (the body-set layer for demos) is not reused: it samples a set's own sources with a per-frame osculating period, while the composition path takes one static span, so the two stay separate. `TimelineEvent` gains optional `object`; `toDefinition` refuses an object the scene lacks (`bad-event`) and the shell's Go to, Previous and Next frame it with the existing Focus preset (I-120; no State change). Label layout keeps one bit of memory per label (shown or hidden by overlap) with a 14 px re-appear margin over the 6 px padding, so crossing labels swap once (I-121; layout only, ARCH-02). The astraeus pack has no file-count limit (owner, O-051 T-218): `tools/check-packs.mjs` fails a packed file that is not a real source module or a file `package.json` `x-publish.files` lists (`strayFiles`); size limits stay.
One path through every stretch (O-050): `addTrajectory`'s `lineFixedTo` is `BodyId | { start, end, body }[] | "auto"`; `TrackedBody.lineFixedTo` holds `string | LineStretch[]` (ms), and `TrackedBodyView` draws the relative trail per stretch (`lineAgainstAt`, `lineBodies` in `app/mission.ts`). A stretch's boundary sample belongs to the later stretch, and time outside every stretch is drawn against the scene centre. `api/pathProvenance.ts` holds one span planner (`planSpans`) behind `planPathProvenance` and `planLineStretches`; `State` and `stateOf` are untouched. `"auto"` is a reserved value resolved by the pure `api/sphereOfInfluence.ts` in `Scene.toDefinition` (or `prepare` when the planet series load late, which replaces the `trackedBodies` entry) into the same list the explicit form takes, so the menu, drawing and follow share one path: each sample is fixed to the innermost scene body whose Laplace sphere of influence `a (m / M)^(2/5)` holds it, the root body holds everything, and a body with no GM is skipped (listed moons added by id have none; Pluto and Charon and the main moons do). Timeline markers (events, story panels, window peaks) are laid out by `groupMarkers` in `shell/timelineModel.ts`: markers closer than `MARKER_MIN_SPACING_PX` (22 px) on the measured track gather into one numbered mark at their mean position whose list opens above the track with each member a full-size button doing what its own marker does; an unmeasured track gathers nothing, and Previous/Next still step every event. The packed package is proved by `check:node-consumer` (listed, `"auto"` and Moon-orbit paths, one menu object each) and by the synthetic journey (`?experience=synthetic-journey`, dev only), whose traveller is drawn against the Sun, Jupiter for 20 days either side of its pass, then the Sun, with Io, Europa and Ganymede passes within nine hours of Jupiter's gathered under one mark; the browser smoke follows the camera across both boundaries and presses each gathered member at 1280x720 and 375x667.

Every listed moon addable (O-049, I-122): the moon lists (458 moons) each carry `orbitPeriodDays` (JPL Planetary Satellite Mean Elements, sidereal P; `tools/import/moon-periods.mjs`, transcribed to `planet-moon-periods.json`). A generated slim lookup `core/bodies/listedMoons.ts` (id, label, mean radius, period, parent, data package `astraeus-data-<parent>`, fit-set body, and an `early` flag for moons whose fits start in 1950, read from the data packages' indexes) is what `addBody` consults, so the full lists stay out of the first download (+19.6 kB raw / +7.6 kB gzip in all). `addBody(id)` for a listed moon the built-in catalogue lacks goes through one rule (`core/bodies/listedMoonBodies.ts`, `assets/bodies/listedMoons.ts`): a grey sphere at the JPL mean radius (the picture pack's picture when registered under the id), positioned by its planet's moon system binding, requiring the planet's data package. The definition and binding extend the scene's own catalogue (`assets/catalogue.extendCatalogueWithMoons`), never the global one; `toDefinition` passes `catalogue` whenever it differs from the built-in one (before: elements bodies only) and `installData` takes it; `MOON_SYSTEMS` moved from `api/data.ts` to `listedMoonBodies.ts`; `MoonSystem.position`/`worstM` is optional (no engine-held worst figure for a listed moon). Public `listedMoons(planet?)` returns the refs with `requires`; `unknown-body` names it. Detailed moons keep their own catalogue definitions and periods; JPL's P for Io and Europa is shorter than the rotation-rate period by 0.36% and 0.73% (apsis not corrected), which does not reach them because they are in the built-in catalogue first, and any later use of the table period for a Jovian moon needs the apsis-corrected rule. T-212 adds Uranus's five main moons (by id, `{ orbit: true }`) and a made-up Uranus pass on 24 January 1986 to the synthetic journey (a scene change, not an architecture change).

Answers for sites (O-045): `Scene.stateOf` answers for every body in the scene through the same state source the viewer draws (catalogue bodies and elements bodies have no data cut-off; only an `addTrajectory` path refuses a date, `bad-time`; planets need the planet series loaded, else `missing-data`). `Scene.provenanceOf` returns the position `Provenance`, which gains optional `accuracyClass` and `maxErrorFraction`; for an elements body the fraction is its class limit (0.01 or 0.05, an upper bound), and built-in Swift-Tuttle's is measured. `CameraReach` gains `fitOrbit` (a lazy farthest Sun distance); the viewer resolves it each frame with the canvas aspect (`liveReach`), so the reach and far plane follow resizing, and `SceneCamera` gains `fitOrbit` and `fitted`. A fitted scene sets no label limit (`setReach` raises the 500 default to the reach); `setReach` and `fitOrbit` share one limit and the later call wins; the opening distance is clamped to the limit like any other. `ProvenanceSourceType` gains `modelled`. Events take their own `provenance` (`ExperienceConfig.eventProvenanceById`, read before the batch `eventProvenance`), and both are validated (`bad-event`). Elements bodies get the live "Distance from Sun" metrics row because `toDefinition` passes the scene's catalogue to `bodyMetrics`. A group's card source type is always "illustrative", with the elements' type in the accuracy line.

Size budgets are split (owner, 2026-11-01, O-051 T-221): the engine has one limit on the plain example's first download (`tools/validate/engine-budget.mjs`, 1,735,000 B raw / 497,000 B gzip, measured 1,652,588 / 472,895 plus 5%), and each demo page's limit in `load-budget.mjs` holds only the page's own share, its first load less the engine's share of it (the browser check's public build writes `engine-share.json`, the rendered bytes per chunk that come from `packages/astraeus/`), so engine growth never trips a demo and demo growth never trips the engine.

Views of one scene (O-051, I-124): `Scene.setViews(views, { place, start? })` names views, each listing the `paths`, `bodies` (bodies and groups), `events` and `panels` it shows plus a `camera` rule; `api/views.ts` checks the shape at the call (`bad-view`) and resolves the ids once in `toDefinition` into `definition.views` (`ViewSettings` and `ResolvedView` in `app/views.ts`; the camera input `{ follow | focus }` becomes rule `"start"` with that framing, a target must be shown by the view). An id no view names shows in every view, so the sky, the Sun-centred sun object and shared bodies need no listing. Switching is presentation only, never a State or clock change (ARCH-02): `App` holds the view id; `viewHiding.ts` computes the hidden set as the ids some view shows that the current one does not (`hiddenByView`), plus every object whose `partOf` is hidden (an orbit line follows its body, so a view never names lines); `SceneControls.viewHidden` carries `{ objects, panels }`, the frame's new `applyViewVisibility` stage (between sync and the placed views' outputs) hides paths, bodies, group dots, composition and orbit-set lines, labels and picks without a rebuild, and `StoryMarkerLayer.update` and the shell's object, event and panel lists take the same sets. The view choice is a button group in the bar and the phone drawer's grid (or rows in the switch panel). The per-view camera rule (`shell/viewCamera.ts`, `useViewSwitch` in `AstraeusShell`) runs once per switch, from the new view's rule, only when the camera's followed or focused object is not in it: `"stay"` sends the new generic `CameraRequest { kind: "hold" }`, which sets `OrbitCameraState.fixedPoint` (the target's current position in the scene frame, tween included) so the target stays put against the scene centre while the clock runs; `switchFocus` clears it and `cameraTargetAbsolute` reads `fixedPoint ?? focusAbsoluteOf`; `"start"` and a framing request that preset. The host link gains the view: `ViewerControl.views`/`setView`, `ViewerState.view` (compared in `ViewerLink.publish`), `MountedScene.view`/`setView`, the `AstraeusScene` `view` prop and `ViewerChange.view`, with cause `visitor` for the buttons and `host` for `setView`; an unknown id or a scene without views throws `bad-view`. Proof: `check:node-consumer` builds three views on two made-up paths from the packed package; `journey-views.mjs` in `check:browser` drives the made-up `synthetic-views` scene (a new scene, so the synthetic journey's own checks and menu stay untouched) at 1280x720 and 375x667.

Bodies reference catalogue definitions and state-source bindings; `StateResolver` composes their positions through the parent chain. Physical state remains independent of camera, selection, scale and rendering. Composed resolver states currently carry position only; velocity composition is a standing limitation. The Moon uses IAU rotation with libration (I-091); tidal locking remains available for other moons. Chebyshev providers load windowed planet and moon fits; validity and sampled accuracy ranges are distinct and must be checked for the chosen dataset.

Scenes expose bodies, bounded trajectories, listed-orbit groups, orbit lines, activity windows, events, story panels, timeline settings, display switches and camera choices. Scene-owned element bodies extend a per-scene catalogue. Groups share the body/path id namespace and use the existing points layer; made-up spreads and moon groups remain internal. See the relevant public-API amendments in reconciliation history for exact options and restrictions.

The app projects state into render coordinates and generic shell readouts. `sceneFrame.ts` runs named frame stages; `scenePointer.ts` owns pointer listeners. The frame loop keeps running for labels and interaction, while idle scenes skip GPU passes after their grace period. Developer panels and the moon-family panel load on demand with error boundaries; planet/comet tables remain synchronous by owner decision.

Apollo and Showers source imports only the public `astraeus` entry and local files; their tests may use engine internals. The site owns demo selection and the shower switch. The local Planets demo covers Mercury to Pluto; the public build offers Jupiter only. Data packages supply optional pictures and moon-position chunks; installing the engine alone gives catalogue stars without the Milky Way picture.

## Boundaries

The engine exports are the package boundary; generic code takes experience content as data. Synthetic configurations prove generic capabilities. Scientific approximation and reconstruction carry provenance and known limits; an accepted sample limitation never becomes a claim of measured fidelity. Planetary Explorer (`/home/user/code/planetary-explorer`) remains a read-only donor.

The mechanised body-name check (`packages/astraeus/tests/nameCheck.test.ts`) covers `src/core`, `src/assets`, `src/shell`, generic `src/app` and, since T-194, the public `src/api/` (guardrail ARCH-06): a public default or rule names a body only through an allowlist entry with a reason.

Browser policy is owned by [browser policy](../docs/agents/browser-policy.md); the scenario/driver map is [BROWSER_CHECKS.md](../docs/BROWSER_CHECKS.md). Gate selection and tooling are in [project gates](../docs/agents/build.md), with ordinary commands in `.savepoint/config.yml`.

## Current Technical State

The package root export has conditions `types`, `node`, `import`: the build generates CSS-free `*.node.js` twins of every compiled file that imports a stylesheet, directly or through imports, so Node and Vitest Node consumers import without an inline setting (`npm run check:node-consumer`); JSON imports carry import attributes. The engine and data packages are built for npm; examples consume packed tarballs rather than workspace links. Apollo and Showers have been rebuilt on the public API. The API reference is generated as a static site page. Current dependency versions, gates, size limits and coverage scope come from their configuration files; historical measurements remain dated evidence in the reconciliation history and cited artifacts.

Code Health uses jscpd for duplication, lizard for complexity and Vitest v8 for coverage. `npm run test:full` refreshes coverage before an official Full Objective Check health snapshot. Maintainer import tools are excluded by owner decision; the exact scope is in `vitest.config.ts`. Scanners exclude the owner's `docs/research` and `docs/prds` notes.
