# Independent engineering audit of Astraeus 0.9.5

## A. Executive verdict

**Keep the architecture. Repair the scientific contracts and narrow the expensive verification paths.** A developer can already build and distribute an Earth–Moon viewer, a heliocentric journey or a meteor-stream experience from public imports. Scientific state, rendering coordinates, scene construction, host control and optional data packages have recognisably different owners. A new story using existing primitives is relatively cheap. A new interaction that affects the shell, camera and host API is considerably more expensive.

The strongest reason to act is reproducibility. Two valid descriptions of the same orbital epoch gave positions **2,154 km apart**. Another scene loading optional moon data changed an existing scene's answer for Jupiter by **143 km**. A separate convergence failure gave a **50.15 million km** radial error for a valid bound orbit. These are reproducible public behaviours, including in a process with no renderer. They outweigh most of the code-style concerns.

Most mathematical and rendering complexity buys something real. The accidental complexity concentrates in presentation orchestration, duplicated numerical conventions and verification that inspects other tests or rebuilds the same artefacts. Scientific fixtures, cold package tests and a small set of genuine browser interactions earn their cost. Running the whole browser itinerary provides diminishing returns on logic already proved at faster layers. Targeted improvement is sufficient. A rewrite would put substantial working science and package compatibility at risk.

## C. Architecture assessment

**13 workspaces, nine publishable.** The engine has one runtime astronomy dependency, pinned Orb, with Three, Fiber, React and React DOM as peers. The package lock and each workspace manifest agree on the functional split below. A `packages/node_modules` directory is not a workspace.

| Boundary / dependency direction | Ownership and evidence |

Time-tagged, centred EQJ vectors, optional velocity/orientation, centre-chain resolution, catalogue bindings and numerical adapters. No scene camera or React dependency needed for a position. |
| Scientific data and assets | `astraeus-data` supplies optional pictures. `astraeus-data-{jupiter,saturn,uranus,neptune,mars,pluto}` each supply a planet's moon index and chunk URLs. `astraeus-data-constellations` supplies sky figures and lookup. | Viewer / host | `api/mount.ts`, `AstraeusScene.tsx`, `viewerHandle.ts`, `viewerLink.ts`. Standalone and React converge on the same handle. Commands arriving around first draw, listener ownership, teardown and scene replacement deserve real lifecycle tests. |
| Renderer and navigation | `app/sceneContentsHooks.ts → sceneFrame.ts`, Three view objects, floating origin, layered passes, camera controller, scene targets and picking. Science feeds the renderer. Build tooling rewrites assets, imports and export maps for distribution. |

ARCH-01/03 have credible mechanisms in `nameCheck.test.ts`, synthetic compositions and four packed examples. ARCH-02 holds for scale, time readouts and camera under ordinary operation. F01 breaks the stronger expectation that the same scene always answers identically. ARCH-04 has a source import scan with planted upward edges (`tests/layerRule.test.ts:25`) plus physical engine-alone verification. A relative-specifier scan has less reach than the isolated build. Demonstration independence is substantially demonstrated, without requiring an abstract renderer interface for every Three operation.

API-01's surface lock, API-02's lifecycle parity and API-06's address scoping are valuable. API-03's control isolation misses scientific cache isolation. API-04 names most units and frames clearly but cannot prevent a numeric JD of one scale being subtracted from a JD of another. API-05 standardises host errors with codes, while external provider/load exceptions can still originate below that boundary (`api/data.ts:72`). API-07 checks data peers, declarations and documentation against source. The broad Three peer range deserves a compatibility smoke check on upgrades. A successful smoke on one version cannot qualify the entire range.

## E. Maintainability and change impact

For the next two to three years the greatest risk is interactions between features with different lifetimes: scene plans, optional scientific data, React attachment, clock seeks, camera transitions and responsive UI. Configuration-based stories are straightforward. Changing how the viewer coordinates those features demands tracing effects and tests across several directories. The docs make the underlying model learnable, though understanding why a specific guard or delay exists often requires a historical Issue.

## F. Extensibility and developer experience

Installation and first scene have a good path: install the engine/compatible peers, import its stylesheet, give the host element a size, add bodies and time, choose a camera, mount and await `ready`. React's `AstraeusScene` offers the same handle. Handle settings support external controls. A missing moon package or a rejected async load happens later than a malformed trajectory field; the host needs to handle both synchronous SceneError and readiness rejection. The engine's `examples/hello-{scene,react,planets,sky}` cover real distribution paths. Node/browser conditional entry points deserve more trust than any workspace-only example.

| Consumer | Verified primitives and plausible integration | Gap / recommended approach |
|---|---|---|
| Asteroid belt | `addBody(sun)`, host filters the orbital catalogue and constructs `addGroup`, `setTimeline`, `setScale`, group appearance and readouts. Measured-shower groups demonstrate a population-scale draw. Gap distributions are input science. | Do not infer individual asteroid picking from group rendering. For a few named objects add bodies separately. An arbitrary dot-to-member pick/lookup at scale needs a stable member identity and picking contract. Medium for illustration, high for a full searchable belt. |
| Voyager | `addTrajectory` with samples or provider, one named input centre, `plane`, `lineFixedTo` stretches/auto, per-span provenance, encounter events, paced timeline and camera follow. Node consumer exercises a made-up 1979 journey. | A line's anchoring differs from the centre of measured vectors. Normalize multi-centre files first. Sparse flyby sampling and historical moon coverage constrain accuracy. Medium, no engine change for a compatible dataset. |
| Ground observer | `camera.lookOut(earth,{direction:{raDeg,decDeg},fovDeg})`, time, stars, sky figures and traces. Verified sky example. | Body-centred RA/Dec does not define a geodetic site, topocentric parallax, horizon or apparent alt/az. | Fictional system | `addBodyFromElements`, `addBodySet`, sampled/provider paths, events, custom panels, views and controls. The public API is coherent for composing an experience, less uniform for extending the physical world model. An additional rendering backend or a speculative plugin framework would bring little benefit. Clarifying the distinct purposes of body, path, body set and point group would improve onboarding more cheaply.

## G. Scientific correctness

**F01 — Scene-local repeatability fails.** Fresh Node process, compiled public entry points, June 1–2 2016. Scene A adds Sun/Jupiter and awaits load. Record `A.stateOf("jupiter", "2016-06-01T00:00:00Z")`. Scene B adds Jupiter/Io and awaits load with the Jupiter data package. Repeat the identical read on A. Position changes from (−809894100.455, 64338846.371, 47294262.491) to (−809893963.850, 64338884.123, 47294282.723) km. `api/data.ts:63` installs into the shared system. `core/bodies/moonSystem.ts:152,181` retains the installed set; `planetTrajectory.ts:26,47` applies its offset. Sharing immutable bytes is reasonable. Allowing another scene to select whether A gets barycentre or centre coordinates is a public scientific error. Pin each resolver's dataset selection. Test A/B load order and simultaneous loads with different sources.

**F02 — Valid high-eccentricity elements silently produce the wrong radius.** A 1 AU ellipse, zero inclination/node/perihelion angles, UTC JD 2451545, e=0.999 and M=0.0058 radians supplied in degrees. At the epoch, the public `addBodyFromElements → stateOf` path returned 57,936,808.35 km. Independently bisecting the monotonic equation E−e sin E=M on [0,π] and evaluating a(1−e cos E) gives 7,783,470.74 km. At e=0.9999 and M=0.0006 the values are 114,592,446.23 and 1,740,070.78 km. A control at e=0.2, M=0.1 agreed to displayed precision. `core/elementsBody.ts:115,248` accepts these inputs. `keplerAnomaly.ts:2–10` applies 50 unguarded Newton steps and returns without a convergence test. Test against a bracketed reference across near-parabolic and ordinary ellipses. This probe concerns initialising an individual body, not the GPU group shader.

**F04 — Equivalent civil and dynamical epochs disagree when using time of perihelion.** A second public probe used a=1 AU, e=0.2, perihelion JD 2451500 TDB, identical other elements. Specify the epoch first as JD 2451545 UTC, then as JD 2451545 + 64.184/86400 TT with `ttMinusUtcSeconds:64.184`. Both denote the same millisecond, 2000-01-01T12:00:00Z. At that instant the state positions differ by **2,153.98 km**. `core/elementsBody.ts:131,211,229` converts the epoch for the clock, then separately subtracts raw JD values of different scales for mean anomaly. The documented TT≈TDB approximation is below 2 ms and cannot account for 64 seconds. Normalise both operands once. Test equivalent UTC/TT/TDB epochs independently of the mean-anomaly input branch.

All three scientific discrepancies reproduced on both Node 22.22.2 and 24.16.0. The probes called public methods of the compiled Node entry using the Perseids parent-body record as a schema template and replacing its orbital parameters. They used no renderer, database or network.

**Independent positive control.** A two-sample public ecliptic-J2000 path along +Y (1 to 2 km over 10 s) returned EQJ (0, 0.9174821431, 0.3977769691) at the start, the expected positive equatorial tilt. The midpoint radius was 1.4999999999999998 km on both forward and backward queries, the endpoint 2 km and a query 1 ms early raised bad-time. The adapter checks input metadata before multiplying AU by 149,597,870.7 km (`core/astronomyAdapter.ts:80–92`). The rotation fixtures separately check Jupiter longitude to 0.02° and document the 0.3–1.2° Mars difference between adopted IAU constants and Horizons (`tests/iauRotation.test.ts:106–120`). These bounds apply to the checked samples.

**Where the evidence is stronger.** State is double precision until the render boundary. `core/state.ts:46,72` validates time, vectors and orientation; `sampledTrajectory.ts:44` enforces bounded, ordered samples and uses Hermite when velocities are available, linear otherwise. Reversing the query order should give the same state for these time-indexed sources. A caller's arbitrary provider can violate that expectation. A curve through anchors is not an uncertainty estimate. Time tables with explicit validity, epoch conversion and SOFA-derived terms exist in `core/timeScale.ts:53–99`. Unix timestamps do not represent 23:59:60 as a distinct Date. Historical pre-1972 civil time and unknown future leap seconds limit precision.

The current planetary accuracy test compares held reference vectors in a known frame, distinguishing planet centre, system barycentre and Sun versus SSB. It rotates Horizons' ecliptic coordinates using 84381.448 arcsec, checks Voyager encounters and annual January 2 samples through 2044, uses a 1 km fit threshold where applicable, separate published offsets and a 40 km pre-1972 ceiling (`tests/planetAccuracyFlybys.test.ts:31,164–218`). This is strong evidence at those samples. A fit to Horizons validated on separate Horizons epochs tests interpolation and transforms, not independent planet theory. Earth, lunar orientation and other moons have different models and tolerances. No universal kilometre accuracy can be inferred. JPL also treats time scale, coordinate centre and frame as separate query choices. [Horizons manual](https://ssd.jpl.nasa.gov/horizons/manual.html)

Apollo's offline `tools/apollo11/dynamics.ts:55` integrates gravity using RK4; `segments.ts:117` joins forward/backward coasts. Runtime playback uses reconstructed trajectories. The reconstruction report preserves raw residuals, an inferred flight-path angle and two inferred speeds. Some corrections exceed 1,000 km. Landing/ascent segments with only two anchors cannot validate intervening guidance. The presentation distinguishes observed events, fitted trajectories and illustrative placement; the comet input itself states that eight checked dates do not bound its accuracy. This candour is valuable. The root README's VSOP87 planetary example at lines 31 and 167 and wording around unbounded dates in `api/scene.ts:591` lag the fitted planet series' actual bounded behaviour (`core/planetSeries.ts:46,61`). Align entry-point descriptions to current providers, while retaining the historical investigations.

## H. Rendering and performance

The frame loop projects 64-bit physical coordinates through the scale policy and subtracts a floating origin before conversion to GPU coordinates (`app/floatingOrigin.ts:2`). Camera, clipping/depth passes, sphere/marker selection, label layout and hit testing are presentation concerns. React manages ownership and events; mutable Three views update from Fiber's frame callback. This avoids re-rendering a component per orbital member. Geometry/material disposal, pointer teardown and texture reuse have dedicated tests. A mounted viewer still consumes browser and GPU resources even when it shares assets with another viewer.

| Workload | Evidence and result | Limit of inference |
|---|---|---|
| Earth–Moon; planetary system | Packed standalone/React examples, phone planet switch, Io focus, close-marker and path tests. Catalogue journey starts a second viewer and stops the first. | Drawing and reachability, no hardware FPS or VRAM measurement. |
| Apollo reconstruction | Current desktop smoke reports 2 bodies, 3 paths, 8,920 stars in its draw readout. Offline numerical reconstruction is independently counted in test timing. | Star count alone would miss an invisible trajectory. No pixel or photometric assertion. |
| Measured stream | 25,588-orbit Perseid workload, public-build readout requiring stream dots in view. Kepler shader uses precomputed P/Q axes and shape attributes. Only uniforms change inside a time window. | CPU-visible sampled count is an estimate. A shader that compiles but renders transparent points may pass. |
| Synthetic population, seeks | Isolated Node 22 CPU microbenchmark on this host, compiled `KeplerPoints`, fixed a=300 million km and e=0.5. For 25,588 / 100,000 members, 1,000 nearby clock updates cost 0.38 / 1.59 ms total; 100 seeks separated by 10¹² ms cost 6.16 / 18.25 ms total. CPU local-position readback for 512 members averaged 0.33 / 0.25 ms. | Single warm process, uniform orbital parameters, no draw, actual driver upload, spatial picking or display sync. Timing order/JIT precludes interpreting the larger case's lower readback time as scaling evidence. |
| Multi-viewer, repeated mount, background tab | Two-viewer DOM/lifecycle tests, packed scene isolation probe, teardown/dispose tests; browser catalogue verifies only one live example after replacement. | No prolonged mount/unmount GPU memory series, measured tab throttling, context-loss/restore test or side-by-side hardware load. |

A rebase rewrites one three-float shape attribute per member (`KeplerPoints.ts:65`), about 1.2 MB marked for upload at 100,000 members. CPU drift control is justified. Point sprites avoid thousands of individual meshes. For non-eligible point groups investigate the interpolation/fill path separately. For the renderer, the most actionable cost is diagnostic projection: `sceneFrame.ts:291–292` calls `sceneDebug.ts:33,47`, which projects path vertices and samples up to 512 points per group, builds arrays and stringifies them into canvas attributes. `PathView.ts:507` walks capacity even when its computed visibility flag is false. The draw rule skips idle WebGL passes but leaves the frame loop running. Lit bodies have separate passes for their own Sun directions, so adding many fully lit meshes has different costs from increasing a point-group population (`LayeredRender.tsx:6–19`). The change-only attribute writer avoids redundant DOM mutations after the computation. F09 identifies paid CPU work; whether it sets the frame limit is unverified. Profile with readouts enabled/disabled before changing their cadence. No fidelity reduction is warranted by these measurements.

## I. Test effectiveness and cost

**Yes for release and objective integration; only partly for day-to-day feedback.** The suite detects wrong frames, broken consumer imports, bad package contents, missing scene content and inaccessible phone interactions. It missed three public scientific defects reproduced in G. A green suite and 94.93% instrumented line coverage are compatible with all three. Vitest skips are not counted as passes. Test value depends on the independence of the oracle, the entry point tested and the inputs varied.

## N. What not to change

* Keep physical state independent from camera and scale. Keep double precision, explicit units and bounded trajectories. CPU/GPU phase rebasing and specialised fit evaluation are justified by the range of distances and times.
* Preserve separate optional moon and picture packages, the public root export, real packed Node test, React peer-resolution/SSR check and four browser examples. Workspace success would have missed the historical bundled-file failure.
* Preserve Horizons source fixtures, known limitations, Apollo raw residuals and inferred override records. Replacing them with generated snapshots of today's answers would remove the independent reference.
* Keep the synthetic alternative scenes and isolated engine build. They test reuse and dependency direction better than a passing Apollo demo alone.
* Preserve real phone hit testing and the public-build stream check. A content count and a happy-DOM click cannot establish a visitor can reach the canvas. Keep the owner's separate visual judgement.
* Keep the independent Full Objective Check. Optimise the work it performs and the fidelity of its evidence before changing its frequency.

## O. Five uncomfortable questions

1. If a scientific answer moves by 143 km when another viewer loads, what exactly does the first viewer's provenance describe?
2. Which inputs is Astraeus prepared to guarantee to external developers: the full interval its types and validation accept, or the subset exercised by its demonstrations?
3. Would the owner accept a visually correct refactor that changes a browser assertion's text, and reject an invisible stream whose CPU readout still says “drawn”? Can the suite make those same decisions?
4. At what point should a new camera or story interaction justify another public contract, given that one App function already coordinates 617 lines of behaviour?
5. If a new contributor has ten minutes to verify a change, which failures should they see first: a changed historical float, a repacked file list, or a physically different answer for the same epoch?
