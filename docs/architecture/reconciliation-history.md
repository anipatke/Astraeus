## Architecture

The Earth–Moon spike has a small framework-independent scientific core and a separate rendering layer. Absolute UTC time feeds dated trajectories and body orientation; explicit center composition and physical Sun directions remain in EQJ kilometres; replaceable scale policies produce fresh render-scale values. A Float64 floating origin and fixed EQJ→render-axis conversion sit downstream, feeding a React Three Fiber scene, a generic viewer shell and app-owned developer diagnostics. Full scientific note: `docs/ASTRAEUS_SPIKE_01.md`; shell decisions: `docs/ASTRAEUS_SPIKE_03.md`.

Since O-014 a third layer sits between core and experiences: `src/assets/` holds the body catalogue (definition from `src/core/bodies/`, state-source binding, visual record, licence), named compositions and the texture files. A `StateResolver` composes any catalogued body to any catalogued centre through the parent chain; the scene mounts the bodies of a composition about a scene centre that is data; paths, scale policies and lighting are generic over the composition. Experiences (`src/experiences/`) are assembled from those parts. The name rule is enforced by `tests/nameCheck.test.ts` (see Interfaces, Name rule). Built-versus-planned record: `docs/ASTRAEUS_SPIKE_04_ASSET_ARCHITECTURE.md`, section "Built".

### O-060 gate timings (moved from docs/agents/build.md, 2026-11-12)

Moved verbatim to keep the gates note short (owner, 2026-11-12, token overhead); `docs/agents/build.md` keeps the operative rules and the limit table.

- Timed gates and time limits (O-060): `tools/gate-limits.json` is the one file that states every limit, in seconds of wall clock. `npm run check:gates` (`tools/time-gates.mjs`) runs lint, typecheck, build, test, test:full, check:engine-alone, check:pack, check:node-consumer and check:react-consumer one after another (or only those named: `npm run check:gates -- lint test`) and prints each time against its limit; `check:browser` prints each step and the total against theirs in its summary. A run over a limit prints a `WARNING:` line and never changes the exit code; only a failing gate does (`packages/astraeus-site/tests/gateLimits.test.ts` plants a limit to prove it). A limit is the slowest time measured plus room for ordinary variation, about 1.4 to 1.6 times (long gates: `test` 41 s to 65 s, `test:full` 72 s to 105 s, `check:browser` 230 s to 320 s), and several times for the short ones whose time is mostly start-up, so a run does not warn while the owner works on other things (T-282 saw `npm test` at 46 s and `check:pack` at 18 s on a busy machine, both within their limits); when a gate grows past its limit, look at why before raising the number. The table below must state the file's numbers, and a test fails if it does not.

| Gate | Before (6aad8e6a) | After | Limit |
|------|------|------|------|
| `lint` | 3.5 s | 3.6 s | 15 s |
| `typecheck` | 5.6 s | 5.6 s | 20 s |
| `build` | 2.3 s | 2.4 s | 15 s |
| `test` | 42 s | 41 s | 65 s |
| `test:full` | 72 s | 72.4 s | 105 s |
| `check:engine-alone` | 25 s | 22.7 s | 40 s |
| `check:pack` | 14 s | 14.2 s | 30 s |
| `check:node-consumer` | 5 s | 4.6 s | 15 s |
| `check:react-consumer` | 9 s | 9 s | 25 s |
| `check:browser` | 353 s | 230 s | 320 s |

#### One handle, one lifecycle

One handle, one lifecycle (O-054, G-016; T-240 to T-249): `ViewerHandle` (`api/viewerHandle.ts`, exported type) holds every read, setter and signal; `MountedScene` is `ViewerHandle` plus `ready` and `unmount`. `viewerHandleOf(link)` is the only builder of the handle: `mount` makes one per call and `AstraeusScene` one per component life (given through the React 19 `ref` prop and `onReady(handle)`, the same object across a rebuild with a new `scene`), so the two embedding paths cannot drift; `tests/lifecycle.test.ts` runs one suite against both. Errors: before `ready` or after `unmount` every read is undefined and every call throws the new code `not-mounted` (`missing-data` now means only missing data packages); listener registration (`onChange`, `onEventZone`, `onSelect`, `onCameraChange`) is exempt, never throws at any time and delivers nothing after `unmount`. `ViewerLink.whenAttached()` rejects with `not-mounted` when `close()` comes before the attach (so `ready` always settles); `ViewerLink.reopen()` takes a closed link back into use for a host effect that was cleaned up and replayed (React StrictMode) before the viewer drew, while a real unmount leaves it closed. The React driver in `lifecycle.test.ts` commits through `flushSync`, which fixed the T-243 StrictMode flake (30 of 30 runs); it is test-only, not architecture. The same T-240 error rule is reflected: a repeated `addActivity` id is `duplicate-id`, a data package whose moon positions name a planet without a moon system is `bad-data` (new code), and the two internal range faults of the sun-orbit code are named error classes in `core/`. Listeners: `api/listeners.ts` is the one helper that calls a set of listeners so a throwing one is reported (`reportError`, else rethrown on a timer) after the others have run; the clock, zone, selection and camera parts all use it. Scene freeze: `prepareScene` marks the scene in a module `WeakSet` (`api/sceneFreeze.ts`, so the public surface gains nothing) and every mutator of `Scene` and `SceneCamera` throws `scene-mounted`; reads (`stateOf`, `provenanceOf`, the scene reads, camera getters) still answer, a scene may be mounted again, and a failed build leaves it editable. Host signals (each a separate part of `ViewerLink`, none of it State, ARCH-02): `ViewerControl` gains required `playable` and `setPlaying` (`viewerPort.ts`; the handle's `playing`/`setPlaying` go through the visitor's own play handler, one clock, `bad-timeline` without a play control); `ViewerState` gains optional `selected` and the link has a fifth part `viewerSelection.ts` (`selected`, `onSelect`, `SelectionChange {object?, timeUtcMs, cause}`; the field is `timeUtcMs` per API-04, as `ViewerChange.timeUtcMs` also is since O-057; a selection dropped because time or the view moved takes the cause of whatever last moved them: `ViewerLink` keeps the cause of the last published clock/view change, and every shell selection path names its origin, a required `SelectionOrigin` argument of `onSelectionChange` (`"visitor"` for the menu, a pick, a preset or a marker; `"move"` for the fallback drop and a view rule's framing target, so a new path cannot omit it), so `onSelect` agrees with `onChange` (`host` for `setTime`/`setRate`/`setPlaying`/`setView`, `playback` for the clock running, `visitor` for the visitor's own moves; I-137); there is no separate selection-cause flag); `ViewerCamera` is stateful (last reported pose, report time, listeners) and is the fourth part `publish` calls (clock, zones, selection, camera), so `onCameraChange` rides the existing 100 ms viewer publish with no new frame-loop work and reports a pose only when it differs, at most about ten times a second. Unawaited `ready` (owner decision, 2026-11-01, "Only hide the expected 'taken down early' case"): `mount` marks `ready` handled only when it rejects with `SceneError` `not-mounted` (an early `unmount`), so a host that never awaits it gets no unhandled rejection for that; any other rejection, such as a failed load, stays unhandled until someone awaits `ready`, as before. Allowlist growth is judged per finding (Decisions, "Allowlist growth counted per finding").

#### Host calls land in order

Host calls land in order (O-061, G-017; T-284 to T-288): after `ready` every host call takes effect or throws, in call order, the last host call winning (README "Host calls"). The camera keeps a host request in its own slot, `controls.hostCameraRequest` (set by `App` on a host `setCamera`, reset by `chooseView` at each view switch): `openFirstFrame` (`app/sceneCamera.ts`) still clears any other request at the opening but keeps the host's, and `applyViewRule` in `AstraeusShell` skips its own hold or framing request when the shell's `hostCameraSet` prop says the host set the camera since the switch, so a view rule is a default a later host call replaces (it still applies its selection change). A view's `camera` framing takes `always: true` (`ViewCameraInput`, `api/views.ts`; anything but `true` throws `bad-view`) to apply the rule on every switch to that view; without it the rule applies only when the switch takes away the followed object. Story panels have one seek re-base: the shell hands `story.noteSeek` (`useStoryPanels`, `CrossingTracker.rebase`) to `App` as `storySeekNote`, and both the visitor's seek and the host link's seek (`App.hostSeekTo`, then `seekTo`) call it, so a host `setTime` opens no panel by crossing. `ViewerHandle.setSelected(id | undefined)` (`api/viewerSelection.ts` through `ViewerLink`, ids checked against `cameraTargets()` as `setCamera` checks them, new code `bad-selection`) goes through the viewer's selection module (`shell/selection/selection.ts`, O-089): `App` calls `selection.ask`, which changes the selection at once (`controls.selectedObjectId` reads it through) and leaves an ask the shell takes last in its view-switch effect, after the fallback and the view rule, opening or closing the object's card as a visitor's menu choice does without moving the camera; while the ask waits the shell's older `choose` is ignored. `ViewerLink.publish` re-reads the viewer state after a nested publish, so a host call made inside an `onChange` report does not leave the rest of that report on the older reading. The opt-in loading cover T-288 built was removed by the owner (hosts fade their own on `onFirstDraw`), so it left no architecture; T-286's one-line test change (I-160, accepted) is not architectural.

#### Good guest

Good guest (O-055, G-016; T-250 to T-258): several viewers share a page without touching it or each other.
- (1) Moon data: `moonSystem.load` fetches per request the chunks its own window, history and year-after need that are not yet held, into one shared append-only store per planet (index fetched once, in-flight dedupe per chunk), so a second scene, a rebuild or a remount of the same planet still gets its moons; a window outside a moon's years still refuses with `out-of-span`; `load` no longer returns the first call's promise.
- (2) Pictures: the page-wide picture book is gone. `BodyVisual` carries `picture` and `desktopPicture` names and `ExperienceDefinition.pictures` carries the viewer's pictures from `data` (`assembleScene`) or hand-built (the site and the planets demo, which import `PICTURES` from `astraeus-data` and hand it in) to `BodyView` (`describeBody(..., pictures)`) and `SkyView` (`pictureSet`); `installData` checks rights but registers nothing, so a viewer draws only the pictures of the packages passed to it.
- (3) Developer tools: `mount` and `AstraeusScene` take `developerTools` (default off, read at build); the shell draws the toggle and drawer only when handed that content and the drawer's code is not loaded otherwise (the whole drawer, header, folds and its readings, is one on-demand component, `app/DeveloperDrawer.tsx`, loaded through `app/developerPanels.tsx` on first open, O-089); the Developer-placed switches and the Copy-view-link button exist only with it (`address: true` alone reads the address, no copy button).

- (5) The engine never looks up page elements: the loading cover is the host's, handed in as the internal `claimCover` prop (`App` to `AstraeusScene` to `FrameState.cover`) and shown, faded or failed by `packages/astraeus-site/src/bootCover.ts`; `mount` and `AstraeusScene` take none. Escape and markers are scoped: `shell/viewerKeys.ts` (`VIEWER_ROOT_CLASS`, `keyIsForViewer`) makes every document key listener of the viewer act only for keys pressed inside its root or on the bare page, `usePanels` (the panel rule's one Escape and outside-press listener) takes the viewer root ref, and the marker layer measures panels inside its own viewer root.
- (6) Styles: `app/style.css` (published as `astraeus/style.css`, the whole look) `@import`s every interface sheet and is the only stylesheet a source file imports; every rule sits under the root class `.astraeus-shell`, which also carries the custom properties (`--astraeus-*` from `shell/look/look.css`, `--perf-*`), `color-scheme`, the base font and the black background, so the viewer owns no page-level style (`html`, `body`, `#app`); `mount` and `AstraeusScene` make their own element a containing block (`position: relative` if static, `overflow: hidden` if visible, a set value kept) and the host sizes it; `mount`'s `unmount` restores the inline `isolation`, `position` and `overflow` the host element had. Specificity convention: where a plain `.astraeus-shell` prefix would let a class rule beat the generic `.astraeus-shell button|select|input|.ui-*` rules, the prefix is written `:where(.astraeus-shell)` to keep the old weight (31 sites, listed in the T-257 evidence); the T-257 builders' static specificity model missed one flip (I-140: an open nested fold heading went accent to muted, because it skipped a `:not()` subject), so the proof is now `packages/astraeus/tests/computedLook.test.ts`, which renders the real App in four layouts, both bundle orders and two definitions and checks that both bundle orders compute the same look element by element (padding, radius, min-height and the look-rule properties) and that named parts keep their token colours (O-088 T-410 retired the whole-page baseline and `look:lock`; the order check found I-194, where the drawer button rule tied the shell's generic button rule and lost in mount order, now `:where(.hud) button:is(button)`; owner "Make both like the site"). The static model is retired, and the root's own rule `main.astraeus-shell` is `.astraeus-shell:is(main)`. The isolation allowlist is empty and the CSS and id scans hold it there. Public surface unchanged apart from `developerTools`; `tests/twoViewers.test.ts` is the two-viewer suite the steps made green.

#### Viewer interface

#### Paths across the solar system

Paths across the solar system (O-046): `addTrajectory` is accepted in a Sun-centred scene (it was rejected). #### Planet positions from Horizons

Planet positions from Horizons (O-063, G-017; T-289, T-290; note `docs/architecture/planet-accuracy-o063.md`): every planet's series in `data/ephemerides/planets/planets.json` is a piecewise Chebyshev fit (as before, made by `tools/import/planet-fits.mjs`) of its system barycentre about the Sun from JPL Horizons, no longer Orb's VSOP87A: for a planet with a moon system the importer fits Horizons' planet centre (DE441 with that planet's satellite ephemeris) minus the centre's offset about its barycentre, and Mercury and Venus are their own barycentre. One binding rule, `planetBinding` / `barycentreOffsetKm` (`core/bodies/planetTrajectory.ts`, bindings listed in `core/bodies/index.ts`), adds the planet's offset from its barycentre from its moon package when that package is loaded (Pluto's old binding made general), so with the package the planet equals Horizons' planet centre (measured under 1 km from 1972; before 1972 up to about 35 km from time labels, UT1 and UTC's rubber seconds against the engine's smooth TT minus UTC) and without it the planet is the barycentre (the measured wobble, up to about 300 km at Saturn). Uranus and Neptune therefore follow their satellite-ephemeris barycentres, which differ from DE441 bodies 7 and 8 by up to 3,441 and 742 km (owner choice). One shared `planetEphemeris` provenance carries the measured figures. Earth keeps its EPV00 model (measured within 7.3 km from 1972). The engine's first download is unchanged: the planet data is a lazy chunk (348,839 B, was 432,063 B). `tests/planetAccuracyFlybys.test.ts` pins the errors against a saved Horizons fixture.

#### Journeys across years

Journeys across years (O-047): a body's positions can cover their own years. A moon-fit `index.json` may give each body an optional `span`; the ephemeris answers a body inside its span, narrowed by its centre's and the time-scale table's (the set-level `span` is informational). A scene whose window leaves a loaded moon's years, or the planet series (1950 to 2045, `planetSeriesSpan()`), fails once at mount with the new `SceneError` code `out-of-span` (moons through `MoonOutOfSpanError` in `moonSystem.load`, planets in the definition's `prepare`, reached by `scene.load` and `mount`). The four planet packages hold the main moons and the planet from 1950 (the rest 2010 to 2030); the fitted-moon time-scale table before 1972 is built from daily samples while the planet series keeps Orb's polynomial, so two UTC definitions coexist there and are not reconciled (accepted limit; the importer's merge writes `span` on every body of a merged set, and a mapped moon's `validUtc` follows its own span). One orbit-line rule, by coverage and never by name: a Sun-circling body is drawn from its own source over one full turn where that is covered, else as the two-body ellipse osculating at the opening time; `fitOrbit`'s farthest distance is settled in setup (`assembleScene`, or `prepare` once the series are in), so a failure reaches the host once. `addTrajectory` takes `provenanceSpans` (resolved against the clock in `infoView` through `spanProvenanceAt`, the one lookup shared with activity windows, so objects are time-dependent like windows). The timeline takes `pacing`: pure `pacedRate` in `presentation/pacing.ts` (log-space smoothstep over spans and event rules; spans (zones with no event) faster than the base set the cruise, the fastest span's blend winning where they meet; slower spans and event rules ease from the cruise, and the paced rate is the minimum of the cruise and of each such piece's blend, so it is continuous at every ramp edge, independent of list order, the slowest wins where slow pieces meet, and the base is exact where none touches, O-069 I-172) which the viewer applies to the one clock (`SceneRuntime.pacing`, `SceneControls.paceAuto`, `ViewerState.auto`, `ViewerControl.paced`). Paced playback integrates the rate rather than reading it once per frame (O-069): pure `pacedAdvance` sub-steps the frame's real time, stopping at each zone or ramp edge and at most 1/32 of a ramp (trapezoid-timed, at most `MAX_PACE_STEPS` 4,096 sub-steps, leftover real time dropped so a hidden tab slows rather than skips); `stepPacing` moves the clock to that time through its public `seek`/`setRate` from where it last left it (`PaceView.last`), and falls back to the one-rate step on the first step, while paused, or after a move it did not make; during a view-switch ease `pacedAdvance` integrates the eased rate (the paced shape times exp(k0 (1 - weight)), k0 being the switch's own change, log start rate minus log paced rate at the switch, fixed on first use in `PaceView.ease.k0`; sub-steps also at most 1/32 of the ease's second), so a zone reached during the ease still slows playback and is entered (clock advance versus real time, 5 ms slack; `seekTo` clears `last`). The clock holds no pacing knowledge; `frameTime` (`app/sceneFrame.ts`) runs the pace step, then wrap or stop, then re-applies the paced rate after a wrap or stop, and `App`'s 100 ms playback tick calls the same `frameTime`, so zone reports follow the slow-downs at any frame rate. Host control is one seam: `app/viewerPort.ts` (the interface `App` is given as `host`) implemented by `api/viewerLink.ts` (`ViewerLink`, validation and `SceneError`s); `App` attaches `{window, rates, read, seek, setRate}` on its one clock and publishes snapshots (`playback` on the 100 ms tick, `visitor` from the timeline handlers), and `ViewerLink.rateSource` (`scene` or `chosen`) is what pacing's override and release use. The public handle gains `timeUtcMs` (`time` until O-057), `rate`, `setTime`, `setRate`, `onChange`; the speed menu shows exactly the scene's `rates` (I-106). Zoom-out (I-114): `CameraReach` gains `cover` (declared by `assembleScene` in a Sun-centred scene that has paths about its centre and no `setReach` or `fitOrbit`): twice the paths' farthest distance, which `liveReach` turns into a widen-only default zoom-out and a far plane of 2.5 times it for the live canvas shape (never narrowing the default, and a declared reach wins), so a path to 170 AU frames whole from any point on it. Playback in a scene with a timeline bar that does not loop stops on the window's edge (`SimulationClock.stopWithin`, the counterpart of `wrapWithin`; `SceneRuntime.stopAtWindow`), because positions past the loaded window were requested every frame once the clock ran on. The made-up `synthetic-journey` fixture (`tests/synthetic/syntheticJourneyScene.ts`, site `?experience=synthetic-journey`, dev only; its moon chunks come from `packages/astraeus-site/src/journeyData.ts`) proves it on the public Scene API with no mission data.

#### Orbit maths (O-082)

One CPU elliptic Kepler solver, `eccentricAnomalyFromMean` in `core/keplerAnomaly.ts`: the mean anomaly is wrapped to (−π, π] (±π returns +π), a cube-root start for e > 0.8, Newton inside a [0, π] bracket with a bisection fallback, a residual or rounding-level stop, at most 100 steps, and `KeplerEccentricityError` for e < 0, e ≥ 1 or NaN. `trueAnomalyFromMean` is built on it; its callers are `satelliteMeanElements`, `bodies/io`, `elementsBody`, `listedOrbitGroup` (`eccentricAnomalyRad` is the shared solve, `trueAnomalyFromMeanRad` delegates) and `sunCentredSources` (adds the whole turns back for an unwrapped anomaly). `keplerElements.fillKeplerRangeKm` keeps its own inline Newton because the shared solve measured 1.46–1.63× slower on a 110,000-member fill; `tests/keplerSolver.test.ts` holds every entry point, the fill included, to an independent bisection for e up to 0.9999. The GLSL solver and its Float32 twin are separate and unchanged. An elements body's epoch is converted once (`epochInstant` in `core/elementsBody.ts`) to UTC ms for the clock and TDB seconds for the anomaly, so `perihelionJdTdb` is subtracted in one scale; a TDB-written epoch keeps the record's "TDB taken as TT" clock convention (≤ ~1.7 ms, planner decision in O-082). Its two-body adapter is built with the centre's own `gmKm3S2`.

#### Errors and labels that tell the truth (O-083)

Every throw a host reaches through the public API is a coded `SceneError`. `Scene.stateOf` refuses by cause: `out-of-span` outside a planet's series years or a moon package's own years, `bad-time` for a moon moment whose data the scene did not load (`EphemerisChunkMissingError`), `missing-data` when the package was not passed; Earth and the Sun have no cut-off. New codes: `bad-scene` (a non-`Scene` given to `mount`, `AstraeusScene` or `load`, from `api/definitionOf.ts`) and `too-many-bodies` (more than `MAX_LIT_BODIES`, derived in `app/sceneFraming.ts` from the layer constants, refused in `assembleScene` at `check`/`mount`); `bad-data` also covers a moon package that cannot be read or parsed; `setViews` refuses an uncopyable value with `bad-view`, `addTrajectory` a non-list `samples` with `bad-trajectory`; `parseElementsBodyRecord` is exported through `api/elementsRecord.ts`, which maps `ElementsBodyError` to `bad-element`. The API-05 scan (`tools/api-rules.mjs`) also judges the throws of functions and classes `index.ts` re-exports from outside `src/api`. `AstraeusScene` without `onError` reports to `console.error`. Moment text is `YYYY-MM-DD` (midnight UTC) or `YYYY-MM-DDTHH:MM[:SS[.fraction]]` with `Z` or `±HH:MM`; `timeInputMs` (`core/timeInput.ts`) returns NaN for anything else, which surfaces as `bad-time`, `bad-panels` or an ignored page `t`. The scale is the closed `ScaleId` (`"true-scale" | "readable-scale" | "solar-system"`) in every public carrier; shell-side inputs (address, experience definitions) stay strings checked at runtime. Mapped moons take definition and binding from one record (`mappedMoon` with `orientationFacts`), so the orientation label and card sentence name the model that turns the moon (IAU rotation where its record gives one, else tidal lock); Io's mean-element trajectory is test-only. Body definitions carry optional `accuracy.positionLimitations` (planets, Earth, the Moon, from their ephemeris records), and cards list position then orientation limits. The resolver composes velocity when every leg has one (`composeCenteredPositions`, `inverseCenteredPosition`); planets, Earth, the Moon and elements bodies stay position-only. Pacing works on the rate's magnitude and keeps its sign, so a negative opening rate paces backward.

#### A lighter frame loop (O-087)

The viewer's frame does less when nothing changed. #### The sky view

The sky view (O-064, G-018; T-291 to T-293): the camera can stand at a body's centre and look out. It is camera state only; nothing in State changes (ARCH-02).

#### Constellations

Constellations (O-067, G-018; T-303 to T-306): the 88 IAU constellations are data in the optional package `astraeus-data-constellations`, never in the engine (the engine knows no constellation, ARCH-01).
- (1) Sources (owner choices recorded in `docs/architecture/constellations-o067.md`): figures from Stellarium's `modern_iau` sky culture (the IAU's figures as drawn by Sky & Telescope, typed in by the Stellarium team, CC BY-SA 4.0), boundaries from Stellarium's Delporte
- (1930) corner points at B1875 (CC BY-SA 4.0), names from the IAU table (CC BY 4.0); each pinned by commit and SHA-256 in `provenance.json`; share-alike applies to the two data files and their adaptations, not to the code (MIT).
- (2) Import (`tools/import/constellations.mjs`, in the package like the other importers): zero-length and repeated figure steps are dropped; xi Ursae Majoris (HIP 55203) is a position end because the engine's star list holds it without a Hipparcos number; boundary edges are chained into closed rings, points added at most 1 degree apart (tighter near a pole) and precessed B1875 to J2000 (not read from the RA-sorted `bound_20.dat`), then cross-checked against CDS VI/49 (0.01 degree tolerance; the run fails above it). Serpens has two outlines (Caput, Cauda) because a `SkyFigureInput` boundary holds one ring.
- (3) Shapes: `figures.json` `abbr -> [[end, end], ...]`, `boundaries.json` `abbr -> [flat [ra, dec, ...], ...]`, `names.json` `abbr -> {name, english, genitive}`; about 66 kB packed, 200 kB unpacked, 10 files.
- (4) Helper: `constellations(which | "all", { outlines, shown, color, labelColor, listed, idPrefix, outlineLabel })` (`outlineLabel` and the separate `constellationFinder()` since O-076 T-320, see the codebase map row) is async (the data load as chunks) and returns `SkyFigureInput[]` for `scene.addSkyFigures`, importing only public `astraeus` types (a data package may hand back engine input through a helper without a deep import); ids are the abbreviation, `<abbr>-boundary` and `Ser-boundary-1`/`-2`; unknown or repeated abbreviations throw `RangeError`; it loads the outline file only when `outlines` is true; cards carry illustrative provenance and no facts (a story app adds those). A Node app can place star-end figures: the star list is read by the same bundled-file reader as the moon chunks (`core/readBytes.ts`: `file:` through `node:fs`, else `fetch`; I-167), and the all-88 test no longer stubs `fetch`.
- (5) Example: `examples/hello-sky` (see the map) is the proof that a plain app needs only `mount`, the helper and story steps; its first download is stated in its README.

#### Headless use and looks as settings

Headless use and looks as settings (O-056, G-016; T-259 to T-264): `scene.load({ data })` loads the planet series and, per moon the scene holds, the chunks its data package provides for the scene's window; a missing load is a typed internal `NotLoadedError` that `stateOf` maps to `missing-data`, and a Node app can pass a package's own `dataSource` because bundled-file addresses of the form `file:` (moon chunks and the star list, one reader, `core/readBytes.ts`) are read through `node:fs` (Node's `fetch` refuses them). `setTimeline` warns (`console.warn`, never throws) when `rate` or an offered rate would cross the whole span in under one real second, the signature of a rate given in milliseconds (I-163). `scene.check({ data })` runs the build checks `mount` runs, without loading or freezing. The scene reads (`bodies`, `paths`, `groups`, `events`, `panels`, `views`, `scales`, `timeline`, and `activities` since O-057; `camera.reachEarthRadii` and `camera.fitted` are members that read the same way) come from the plans (`api/sceneReads.ts`) and replaced every `toDefinition` read when O-057 removed it (migration table in the CHANGELOG). Looks are one table, `app/look.ts` (`resolveLook(base, search)`, ranges written once, read by `Scene.setLook` through `api/look.ts` `LookInput`), with precedence address, then `setLook`, then the value saved from the Developer drawer, then the default; a live `handle.setLook` wins over the address, and the viewer seam (`ViewerState`, `ViewerControl`, `ViewerChange`) now carries scale, look and switches, the live look held in the scene's controls (`app/liveLook.ts`). Sky is built for every viewer, hidden or not, so a hidden-sky viewer still loads the star catalogue. Event zones are independent of pacing: `EventInput.withinSeconds` gives an event its own zone, `ExperienceDefinition.eventZones` lists every event zone (rule zones first, then own zones; order is not contract) and the host zone report reads it; `presentation/pacing.ts` holds `EventZone`, `zoneAround` and `eventZonesOf`. The third example, `examples/hello-planets`, is the proof that a plain app with no probe needs only these calls.

The time look (O-074, T-316): `LookInput.time` `{ zone, precision }` (`app/timeLook.ts`, two spec kinds `zone` and `choice` in `app/look.ts`, both with no address parameter, like `labels`) sets how the viewer writes times; `SceneControls.timeLook` holds it (`applyLook`, `lookReadOf`), App state mirrors it, and `AstraeusShell`'s `timeLook` prop hands it to `TimelineBar` and `infoView`. `formatTime` (`shell/timelineModel.ts`) is the one formatter for the clock bar, slider text, bound dates, event list and event/window info cards: `"UTC"` keeps ISO text (to the second identical to `formatUtcTimestamp`), a visitor's or named zone uses `Intl.DateTimeFormat` in the visitor's language. `<time dateTime>`, `DebugOverlay` and the page address stay UTC; times in the API stay UTC milliseconds (ARCH-02).

Panels, controls and reads (O-075, T-317 to T-319): a moment panel closes once forward playback passes its time plus `closeAfterSeconds` (the panel's own, else `setStoryPanelPlayback`'s; absent never closes), decided by the pure `panelCloseMs`, `panelArmedAt` and `panelSpanPassed` beside `CrossingTracker` (`shell/storyPanels.ts`) and called each tick from `useStoryPanels` (I-179): a panel is armed when it opens while the clock, as `CrossingTracker.timeUtcMs` holds it after any seek the open makes, is before its close moment, and an armed panel closes on the first forward-playing tick after its opening tick that ends at or past that moment; one opened at or past it without moving the clock stays open. A seek, rewind or pause closes nothing, and a close reports `onPanel` cause `playback`. The phone sheet cap is the look `sheetMaxPercent` (30 to 85, default 50, no address parameter), held once in `SceneControls.sheetMaxPercent`; App's phone layout and the Developer "Sheet height" slider read and write that value. `UNIT_SUFFIX` in `tools/api-rules.mjs` accepts `Percent`. The camera plan gains `setFocusChoices` and `setOverview` beside `setFollowChoices` and `setLookOutChoices` (their state in a module `WeakMap` read by `cameraChoicesOf`, not public getters); `cameraPresetsOf` takes one choices object, `checkOpeningChoices` refuses an opening follow or focus outside its choices, and `ExperienceConfig.focusListed` (set only when focus choices are given) stops the shell's plain-focus fallback; with no Overview preset the shell's overview fallbacks hold the pose. The scale switch hides with `setScale(x, { only: true })`, as before. A switch `label` runs `switchesOf` -> `DisplaySwitchSetting.label` -> `displaySwitchItems` (else `DISPLAY_SWITCH_LABELS`) to the top-bar button and panel row; the Developer drawer keeps its fixed controls. Scene reads `look` (`lookReadFrom` in `app/liveLook.ts`, the resolvers `initialSceneControls` uses, so it equals a fresh `handle.look` with no address; `sunGlow` only when an added body carries a halo; `loadFadeSeconds` through `bootFadeSeconds`, so a Developer-drawer saved value shows), `switches` (`{ place, on, label? }`), `panelPlayback` and `timeline.pacing` (span ends read as `spanStartUtcMs`/`spanEndUtcMs`) are Node-readable; the handle's reads are unchanged.

#### Time windows and rates (O-010): O-073 additions

Opening and edges (O-073 T-314): `setTimeline({ playing })` (default true) plans `definition.clock.playing`, which `openClock` reads before the first frame, and `scene.timeline.playing` reads it (a frozen `{ none: true }` scene reads false). `Clock.stopWithin` pauses before it seeks, so a stop at a timeline edge lands exactly on it, and `CrossingTracker` counts a stopped tick right after a playing one as playback, so a moment panel at the end opens; a seek never does.
