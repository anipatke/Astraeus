# Astraeus map audit (read-only), 2026-10-21

Method. SHA-256 and sizes by script over `src/assets/textures/*` against the donor `public/textures/*` and every `data/bodies/*/map.json` record. For orientation I drew every `features.json` marker onto the file Astraeus draws, using the donor/Astraeus marker maths (`FeatureMarkers.ts` `latLonToXYZ`): marker lon m sits at u=(m+180)/360 (image centre = marker lon 0, east to the right), v=(90-lat)/180. I then VIEWED each annotated image (scratch: `.../scratchpad/v/<body>.jpg`) and checked that well-known features sit under their markers. Tool used: ImageMagick plus a small python script; nothing in the repos was touched.

Two separate questions are reported, because they fail separately:
- A. In-frame: do the tagged places sit on the right terrain in the picture Astraeus draws (the owner's complaint for Venus)?
- B. Physical: is the picture's centre longitude 0 E (what `textureYawRad` 0 needs)? `docs/DONOR_PROVENANCE.md:30` records that the sphere puts image-centre longitude 0 on mesh +X, so a map centred on 180 E needs `textureYawRad` = PI to match IAU rotation. Earth and Moon were verified by eye there; I verified the others by locating features of known IAU longitude. Where B is wrong the markers still sit on the right terrain (they rotate with the mesh), but the globe faces the wrong way in the real sky.

"Viewed" = I looked at the annotated image. "Inferred" = reasoned from records/docs, not seen.

## Findings by severity

### HIGH

1. Venus draws the wrong image. `src/assets/bodies/venus.ts:4` imports `venus-2k.jpg` (SSS, turned 180 deg against Magellan); `data/bodies/venus/map.json` and `features.json` describe the donor `venus-2k-balanced.jpg`/`venus-8k-balanced.jpg`. `docs/DONOR_PROVENANCE.md:79` records that the balanced Venus "was not used". Smallest faithful fix: copy `venus-2k-balanced.jpg` (sha 5ccac073.., USGS/NASA Magellan, public domain; credit USGS/NASA, README entry in map.json), point `venus.ts` at it with a public-domain `AssetLicence`, keep `textureYawRad` 0 (the balanced image is centred 0E: Maxwell at 3E, Aphrodite at 110E both under their markers, viewed), update DONOR_PROVENANCE:76 and the licence/credits text. If a stopgap is wanted, yaw PI on the SSS map only aligns the continents, not the data, so do not do that.

2. Titan markers are placed by the wrong rule. `data/bodies/titan/map.json` `conventionNote`: "stores source west longitudes directly, without the 180 - west remap". The image has 360W at the left edge, so a west longitude W must be shown at m = 180 - W. Evidence in the Table (Xanadu 20 deg off, Huygens 180 deg off, Sinlap 148 deg off; the stored Huygens value 192.3 is actually an east value). Not an Astraeus bug: `features.json` is frozen as the donor's (data/bodies/README.md); the donor has the same error on its own globe. Smallest faithful fix is the owner's decision because the data are declared "exactly as held": either leave them and record a catalogue oddity, or add a per-body marker transform (m = 180 - W for source-west entries) in the importer and re-verify Kraken/Ligeia/Ontario/Belet/Shangri-La/Xanadu/Menrva/Sinlap/Huygens against the picture. Not a one-line fix; I did not guess the Titan values.

### MEDIUM (physical orientation; marker/terrain agreement is intact)

All are `textureYawRad` values in `planetSystemMaps.ts:25` ("no map has been checked against its body's prime meridian yet") and `galileanMoons.ts`. Needed values, from the centre longitudes I measured:

- Set `textureYawRad` = Math.PI (image centre = 180E) for Pluto (`planetSystemMaps.ts` PLUTO_VISUAL, via `sphere()`), Tethys, Dione, Rhea, Iapetus, Titan, Europa (`galileanMoons.ts:46`), Callisto (`galileanMoons.ts:48`). Sign does not matter for PI.
- Set Ganymede `textureYawRad` to 0 (`galileanMoons.ts:47`, currently Math.PI), because the donor already re-centred the picture to centre 0E.
- Keep 0 for Mimas, Charon, Io, Triton, Mars, Mercury, Moon, Earth, and the balanced Venus.
- `sphere()` in `planetSystemMaps.ts:45` takes no yaw argument; the smallest change is a yaw parameter with default 0.
- Caveat: this assumes mesh +X = IAU longitude 0 for each body, which `DONOR_PROVENANCE.md:30` confirms only for Earth and Moon (by eye). Tidal-lock sanity checks supporting the PI cases: Iapetus' dark side must lead (90W) and Tethys/Dione/Rhea's dark trailing hemisphere must be at 270W; both are 180 deg off with yaw 0. The owner should confirm one of them on the preview before the batch is applied.

### LOW

- Records vs drawn: Earth (BMNG 4k), Moon (LROC 2k), Jupiter (own 2k), Dione/Triton/Pluto (4096 resizes) all differ from their `map.json` sha by design; each is documented (DONOR_PROVENANCE:24, :89, planetSystemMaps.ts:11). Suggest adding a `drawn` note to those map.json files only if the owner wants the record to equal the pixels; nothing is wrong with the images.
- Quality: Astraeus ships one variant per body. Donor desktop variants not used: Mars 8k, Mercury 8k, Venus 8k, Saturn 4k, Io 4k, Ganymede 4k, Jupiter 4k, Moon 4k/8k. Charon is 1024 px. The donor draws no cloud or bump layers (only code-drawn atmosphere shells on Earth, Jupiter, Saturn, Uranus, Neptune, Titan); Astraeus draws an atmosphere only on Earth.
- Saturn's hexagon and Jupiter's GRS marker have no matching feature in the SSS pictures (Saturn hexagon not visible; GRS 30 deg off): cosmetic, features are not fixed in longitude.
- Licence in passing: Venus current text says CC BY 4.0 SSS; after the fix the licence becomes USGS/NASA public domain (credit USGS Astrogeology / NASA Magellan). Iapetus comes from a Wikimedia copy (recorded). Ganymede licence is inferred from the donor credits list (recorded as a T-098 drift note). Nothing newly out of line found.
