# Astraeus 0.8.0

## astraeus 0.8.0 (2026-11-07)

First download of the packed example (`npm run measure:example`): 1,716,429 bytes raw, 492,249 bytes gzip (code and styles loaded on first open), against 1,652,632 raw and 472,929 gzip at 0.7.0.

A modular, consumable package (G-016, O-053 to O-060): one front door, the same abilities from `mount` and React, a viewer that behaves as a good guest on any page, numbers without a viewer, looks as public settings, standalone event zones, consistent names, units and shapes, and a scene builder split by concern. This is a clean break: old names are removed, not aliased. Apps built on 0.7.0 follow the migration table below.

### Migration from 0.7.0 to 0.8.0

This one table lists every change an app built on 0.7.0 must act on, from O-053 to O-059 and from the renames of O-057. Old names are removed, not aliased: TypeScript flags each one, and a plain JavaScript caller who passes an old input name gets a `SceneError` with code `renamed` naming its replacement. Each row is checked against the 0.7.0 surface and `api-surface.lock.json` by `packages/astraeus-site/tests/migrationTable.test.ts`, which also fails if a change between them has no row; `behaviour` rows hold what no type can show. The step entries further down were written as each step landed and keep the words of that day; where they differ, this table wins.

Changed (O-057 T-280, I-147, I-148, G-016, breaking before 0.8.0): `TextureRef.desktop.minViewportWidth` is refused with `renamed` naming `minViewportWidthPx`, in a `pictures` entry of a data source, like the other old input names. The checks a data source needs no loading for (a picture without rights or with an old name, moon positions with an old name or a planet with no moon system) now run at `scene.check` as well as `load` and `mount`, so `check` throws what `mount` would.

Changed (O-057 T-280, I-145, G-016, breaking before 0.8.0): a repeated event id throws `duplicate-id`, inside one `addEvents` call or across calls, like every other `add*` call (it threw `bad-event`).

Changed (O-057 T-279, G-016, breaking before 0.8.0): the catalogue holds only the Sun, the planets, Pluto and the moons. Comet 109P/Swift-Tuttle is no longer built in: `scene.addBody("swift-tuttle")` throws `unknown-body`, like any id the catalogue does not hold, and the `renamed` code is not used because the body is not renamed but gone. Add a comet or asteroid with `scene.addBodyFromElements(record)`; the Showers demo does this for Swift-Tuttle from its Perseids settings file, with positions identical to the old built-in body (the largest difference over 285 dates from 1990 to 2030 is 0 km). The engine no longer exports `SWIFT_TUTTLE` or `SWIFT_TUTTLE_SAMPLING` from its body index, and the whole-orbit line of a body now comes only from its own source or its record's sampling (no body is drawn by name).

Changed (O-057 T-278, G-016, breaking before 0.8.0): story panels are typed, checked at the call and honest about their sources. `addStoryPanels(list)` takes a list of `StoryPanelInput` and appends: a bad shape throws `bad-panels` at the call naming the panel and field, a repeated id throws `duplicate-id`, and links to events, anchors and objects are still checked at `check` and `mount`. `provenance` (`{ sourceType, sources, accuracy, notes }`) replaces `badge` and `sources`, with no second way: the badge shows the word for `sourceType`, so it can also read Ephemeris or Reconstructed, and the folded section shows the accuracy and notes above the sources. `at.utc` is `at.time`, a `TimeInput`, so text without a Z, a `Date` and Unix milliseconds all work. `pauseSeconds` and `autoOpen` move to `scene.setStoryPanelPlayback({ pauseSeconds, autoOpen })`, which replaces the whole setting. `scene.panels` carries `provenance` in place of `badge` and `sources`. `StoryPanelsInput` is gone; `StoryPanelInput`, `StoryPanelAt` and `StoryPanelPlaybackInput` are exported. A plain JavaScript caller who passes `badge`, `sources`, `at.utc` or the old `{ panels, pauseSeconds, autoOpen }` object gets `renamed`, naming the replacement.

Changed (O-057 T-277, G-016, breaking before 0.8.0): what the viewer reports carries its unit, and orbit records say `plane`. `ViewerHandle.time`, `ViewerChange.time` and `EventZoneChange.time` are `timeUtcMs` (Unix milliseconds UTC), on `mount` and on `<AstraeusScene>` (`ref`, `onReady`, `onChange`, `onEventZone`); the React `time` prop and `setTime` are inputs and keep their names. `ElementsBodyRecord.frame` is `plane`, and `accuracy.validFromUtc` and `accuracy.validToUtc` become `accuracy.valid: { start, end }` (ISO text as before, or a `Date` or milliseconds). `addBodyFromElements` and `parseElementsBodyRecord` refuse the old names, naming the replacement (`renamed`, or `bad-element` from the parser). `State.frame` and `CenteredPosition.frame`, which `scene.stateOf` returns, are `plane` (the value is still `"EQJ"`), and `TextureRef.desktop.minViewportWidth` is `minViewportWidthPx` (CSS pixels, compared with `window.innerWidth`). See the migration table above.

Changed (O-057 T-276, G-016, breaking before 0.8.0): the names a caller gives follow one rule (API-04: the unit in the name, `center`, spans as `{ start, end }`), and the old names are removed, not aliased. `MoonPositions.centre` is `center`, and `loadIndex` returns a `MoonIndex` (new type export) instead of `unknown`, in the engine and all six `astraeus-data-*` packages. Pacing is `{ start, end, rate, rampSeconds }` and `{ near: { type, withinSeconds }, rate, rampSeconds }`. `camera.lookAt` is `camera.focus`. A view lists one `objects` list in place of `paths` and `bodies` (a body, group or path id; `events` and `panels` stay). `labelReach` is `labelReachEarthRadii` on `addBody` and `addTrajectory`, and the `camera.reach` read is `camera.reachEarthRadii` (`setReach` keeps its name). `plane` is required on `addGroup`: a group without one throws `bad-group`, where it once defaulted to `"ecliptic-j2000"`. A plain JavaScript caller who still passes an old input name gets a `SceneError` with the new code `renamed`, whose message names the replacement; see the migration table above.

Changed (O-057 T-274, G-016, breaking before 0.8.0): the scene's internal output leaves the public API. `Scene.toDefinition()` and `Scene.missingData()` are removed (use `scene.check({ data })`, `await scene.load({ data })` and the reads `scene.bodies`, `paths`, `groups`, `bodySets`, `events`, `panels`, `views`, `timeline`, `activities`); `SceneCamera` is now exported as a type only (reach it as `scene.camera`; it can no longer be built by a host); `RateSource` is no longer exported (it was only the type of an internal field of the viewer's link). Added: `scene.activities`, a fresh frozen list per `addActivity` of `{ id, label, unit, windowStartUtcMs, windowEndUtcMs, peak: { label, value, timeUtcMs? }, samples, provenance?, type? }` (type `SceneActivityRead`).

Added (O-057 T-275, G-016): the root names every type a host can reach. New type exports: `BodyId`, `DisplaySwitchId`, `DisplaySwitchPlace`, `ViewPlace`, `ViewerChangeCause`, `LineStretchInput` and `TrajectoryBase` (the fields shared by the `TrajectoryInput` variants), and the types behind already-named ones: `CenteredPosition`, `Quaternion`, `FrameId`, `CenterId`, `ElementsSource`, `ElementsTimeScale`, `LocalOnlyDeclaration`, `PublicReplacement`, `SolarSystemScalePolicy`. Types only; nothing existing changes.

O-059 (G-016) moves the planets demo and the site onto the public API. The new public parts below (T-266 to T-269) are what they needed, each general and with a default; T-265 and T-270 to T-272 are not API entries: the place lists moved to `astraeus-data`, the moon lists and fit errors to `astraeus-data-<planet>`, and the private `App` props, definition `switcher` and boot-cover code were deleted, none of which was public.

Added (O-059 T-269, G-016): a picker an app offers in the viewer's top bar and phone drawer, and a signal for what the visitor picks. `scene.setPicker({ id, label, options, value })` (`PickerInput`, options `{ value, label }` as `PickerOptionInput`; fewer than two options draw nothing) and the read `scene.picker`; on the handle, the same from `mount` and `AstraeusScene`, `handle.pick` (the pressed option's value), `handle.setPick(value)` (moves it, no signal) and `handle.onPick(fn)` (`fn({ picker, value })`, a `PickChange`, when a visitor presses an option other than the pressed one), and the `onPick` prop of `AstraeusScene`. The viewer only reports the press: it never navigates, reads or writes the page address, or keeps a time, and the pressed option stays until the host calls `setPick` or builds a new scene; a host keeps the clock across a choice by reading `handle.timeUtcMs` in `onPick` and calling `setTime` on the next scene. New error code `bad-picker` (a malformed picker, an unknown `setPick` value, or `setPick` on a scene without a picker). Nothing existing changes.

Added (O-059 T-268, G-016): `scene.setMoonPanel({ label, families, featuredFamily?, listSource?, listDate? })` shows the sliding moon panel (families of `{ id, label, description, moons }`, a moon being `{ id, named? }`, a body or body-set member of the scene; pictures come from the viewer's `data`), `scene.addPlaces(body, { categories, places, provenance, knownLimitations? })` draws tagged surface places on a body (`PlaceInput`: `id`, `name`, `kind`, `category`, `latitudeDeg`, `longitudeDeg`, `description`, `details?`). New reads `scene.moonPanel` (`count`, `summary`) and `scene.places` (`body`, `count`), new error codes `bad-moon-panel` and `bad-places`, and the types `MoonPanelInput`, `MoonPanelFamilyInput`, `MoonPanelMoonInput`, `PlacesInput`, `PlaceInput`, `PlaceCategoryInput`, `SceneMoonPanelRead` and `ScenePlacesRead`. The place lists of 24 bodies moved from the engine's `data/bodies/` to `astraeus-data` (`astraeus-data/bodies/<body>/...`), published for the first time with a NOTICE line.

Added (O-059 T-267, G-016): `scene.addBodySet(input)` draws many small bodies about one centre as one batch (dots with a pixel floor, a ball at true size close up, names on hover, tap or near zoom, orbit lines coloured by family), each member selectable with an info card. `BodySetInput`: `id`, `center?`, `families` (one to sixteen of `{ id, label, color?, brightness? }`), `members`, `bodies?` (bodies added with `addBody` that belong to a family; one with no `orbit` of its own gets its line in the batch), `provenance`, `centerGmKm3S2?`, `balancePoint?` (`{ body, gmKm3S2 }`) and `orbitHistoryMs?` (default 0; asks the moon loader for that much before the window). A member is a listed moon of the centre (no `elements`; positions come through `data`, label and radius default to the list's) or a made-up one on two-body motion (`elements` with `time?` and `plane?`; `label` and `radiusKm` required); a set is one kind or the other. Members take `description`, `facts`, `provenance`, `knownLimitations` and `listed` (default false) as `addBody` does. Migration: in an app built on 0.7.0, replace any polling of `handle.camera` on a timer with `handle.onCameraChange(...)`; nothing else changes.
- The host can read which object is selected and hear when it changes (O-054 T-247, G-016). `ViewerHandle` (from `mount` and from `AstraeusScene` `ref` and `onReady`) gains `selected` (the id of the object whose information is open; undefined before `ready`, after `unmount` and when nothing is selected) and `onSelect(listener)`, which calls `listener({ object?, timeUtcMs, cause })` only when the selection differs from the last report (the opening selection is read, not reported) and returns a stop function; the new type `SelectionChange` is exported. Read only: no setter. Migration: in an app built on 0.7.0, replace any reading of the viewer's object menu or a poll of the page for the selected object with `handle.selected` and `handle.onSelect(...)`; nothing else changes.
- The host can pause and play the viewer (O-054 T-246, G-016). `ViewerHandle` (from `mount` and from `AstraeusScene` `ref` and `onReady`) gains `playing` (undefined before `ready` and after `unmount`) and `setPlaying(boolean)`, which goes through the visitor's own play handler (one clock); `onChange` hears it with `cause: "host"`. A non-boolean, or a scene with `setTimeline({ none: true })` (no play control), throws `bad-timeline`; before `ready` or after `unmount`, `not-mounted`. Migration: in an app built on 0.7.0, replace any click on the play button or `rate` workaround for pausing with `handle.setPlaying(false)` and read `handle.playing`; nothing else changes.
- A scene is frozen once a viewer takes it (O-054 T-245, G-016). After `mount(element, scene)` or an `<AstraeusScene scene>` build, every `add*`, `set*` and `scene.camera` edit (`follow`, `lookAt`, `setReach`, `fitOrbit`) throws the new `SceneErrorCode` `scene-mounted` instead of being silently ignored; `stateOf`, `provenanceOf`, `missingData` and the camera getters still answer, and the same scene can be mounted again, also into a second element. A build that fails (an empty scene, a missing data package) leaves the scene editable, and `toDefinition` on its own does not freeze. Migration: in an app built on 0.7.0, build a new `Scene` instead of editing one already mounted, and pass it as the new `scene` prop or mount it again.
- One throwing listener no longer silences the others (O-054 T-244, G-016). `onChange` and `onEventZone` listeners (the handle's, the scene option and the React props) are all called through one helper: a listener that throws is reported to the page with `reportError` (else rethrown on a timer) after the rest have run. Migration: none needed; in an app built on 0.7.0, an error thrown in one listener now shows up as a page error instead of cutting off later listeners, so remove any try/catch kept only to protect them.
- Package ranges now state what was tested (O-053 T-230, G-016). The engine's `react` and `react-dom` peers are `>=19 <20` (all of React 19; they stopped at `<19.4`), checked by installing the latest React 19.x into the packed engine (`npm run check:react-consumer`). Each `astraeus-data*` package's `astraeus` peer is the engine's current minor, `>=0.7.0 <0.8.0` today, instead of `>=0.1.0 <1.0.0`. The engine now exports `./package.json`, as the data packages already did.
- Every `SceneErrorCode` now carries a doc comment that says what it means (O-053 T-229, G-016); the README error table is generated from them (`npm run api:errors`). The set of codes is unchanged; only the comments in the lock's `SceneErrorCode` signature differ.
- React apps get the same handle as `mount` (O-054 T-242, G-016). `AstraeusScene` takes a React 19 `ref` prop that receives the `ViewerHandle` (one object for the component's life, also across a rebuild with a new `scene`; reads `undefined` and calls throw `not-mounted` until drawn and after unmount), and `onReady` now receives that handle. `onReady` under React StrictMode fires once per build, after the viewer has attached (before, the replayed effect closed the link for good and it never fired); the `camera` prop is compared by value whatever the key order of a pose. `mount` and `AstraeusScene` build the handle with one shared helper. Migration: in an app built on 0.7.0, read and set through the handle from `ref` or `onReady(handle)` (the props stay as shortcuts); an `onReady` that took no argument keeps working.
- The mount handle has one shared type and an honest error before and after use (O-054 T-241, G-016). New exported type `ViewerHandle` holds every read, setter and signal of the handle; `MountedScene` is `ViewerHandle` plus `ready` and `unmount`. New `SceneErrorCode` `not-mounted`: any handle call before `ready` or after `unmount` throws it (was `missing-data`, which now means only missing data packages), and `ready` now rejects with it when `unmount` comes before the viewer is drawn (it used to stay pending or resolve unusable). Migration: in an app built on 0.7.0, catch `not-mounted` instead of `missing-data` for handle calls made before `ready` or after `unmount`, and handle (or ignore) a rejected `ready` after an early `unmount`.
- Errors follow one rule (O-054 T-240, G-016). A repeated `addActivity` id now throws `duplicate-id` (was `bad-activity`), like every other repeated id; a data package whose moon positions name a planet without a moon system now throws `SceneError("bad-data")` (new code; was a `RangeError`); a `lineFixedTo` stretch with no body is a `bad-trajectory` `SceneError` throughout; the sun-orbit code recognises its two internal range faults by named error classes (still `RangeError` subclasses) instead of by message text. Migration: an app that catches `bad-activity` for a repeated activity id should catch `duplicate-id`, and one that catches a `RangeError` from a bad data package should catch `SceneError` code `bad-data`.
- The host hears when playback enters and leaves a flyby (O-052 T-226, G-015). New `MountedScene.onEventZone(listener)` and `AstraeusScene` prop `onEventZone` call `listener({ event, type?, object?, entered, time, cause, via })` (`via` is `"time"` for playback or a seek and `"view"` for a view switch that showed or hid the zone, so a host restores a camera only for `"time"`) as playback crosses, or a seek or view switch moves across, the zone of a pacing `near` rule for an event the showing view has (`cause` `playback`, `visitor` or `host`); `MountedScene.eventZones` reads the active event ids. A zone already active when the viewer opens reports `entered` once after `ready`. New exported type `EventZoneChange`. The engine builds in no camera behaviour: the README's "camera to the encounter" example composes `onEventZone` with `setCamera` and `camera`. No new event field and no pacing option.

- Pacing follows views (O-052 T-224, G-015): in a scene with `setViews`, a `pacing` event rule `{ near: { type, within }, rate }` now slows playback only near the events the showing view has; in 0.7.0 every view slowed at every event of the type. Spans apply in every view. - The viewer leaves the page address alone unless asked (O-052 T-223, G-015). Behaviour change from 0.7.0, which read and wrote the address regardless; pass `address: true` for it (the demo site does). The README's new "Page address" section lists every parameter. A new test fails if source outside `src/app/address.ts` reads the address.
- `ready` means usable (O-052 T-222, G-015): `mount`'s `ready` resolves, and `AstraeusScene`'s `onReady` fires, only once the viewer has attached its clock, so `time`, `rate`, `view`, `setTime`, `setRate` and `setView` work straight after `await ready`. In 0.7.0 `ready` resolved about two frames earlier and `await ready; setView(...)` threw `missing-data`. A load failure still rejects `ready`; `unmount` before the viewer is drawn never makes it usable. No change to the handle's shape or error codes.
