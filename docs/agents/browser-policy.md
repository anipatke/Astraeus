# Browser validation policy

Owner decisions (2026-10-17 to 2026-10-23); read before browser validation or changes to its scripts. This file decides which browser steps run when; the commands, what each step protects, where results go and how to diagnose a failure are in [BROWSER_CHECKS.md](../BROWSER_CHECKS.md).

- **Browser tiers (owner decision 1 of G-024, O-086; lightened by O-094 T-424, owner ticks P01 and P02, 2026-11-22).**
  - A Full Objective Check runs one browser command once. By default it is `npm run check:browser -- --tier quick --skip-examples`. When the Objective's diff touches any path in the list below it runs the quick tier plus the `look-out` step instead: `npm run check:browser -- --tier quick --step look-out --skip-examples`, adding `--step <name>` for each other full-tier step whose own paths (the second list) the diff touches. A release runs the full tier (`npm run check:browser`, or `-- --tier full`), every step including the four packed examples. When unsure whether a path counts, add its step. The steps are chosen by the checker from the diff; no script picks them.
    - Camera: `packages/astraeus/src/app/CameraController.tsx`, `sceneCamera.ts`, `viewUp.ts`; `packages/astraeus/src/api/cameraRequest.ts`, `planCamera.ts`, `viewerCamera.ts`.
    - Layout: `packages/astraeus/src/shell/` (shell and panel components) and any `.css` file under `packages/astraeus/src` or `packages/astraeus-site`.
    - Shaders: any GLSL, and any `onBeforeCompile` use (today `packages/astraeus/src/app/PointsView.ts`, `KeplerPoints.ts`, `dotMaterial.ts`).
    - Sky: `packages/astraeus/src/app/SkyView.ts`, `SkyFiguresView.ts`, `sceneSky.ts`, `skyFigures.ts`, `skyModel.ts`; `packages/astraeus/src/api/planSkyFigures.ts`, `skyFigureInput.ts`, `skyTraceInput.ts`; `packages/astraeus/src/presentation/skyTrace.ts`; constellation and star code and data, including `packages/astraeus-data-constellations/`.
    - Packaging: `tools/build-*.mjs`, `tools/check-packs.mjs`, a `package.json` `exports` or `files` field, and `examples/`.
  - The other full-tier steps, each added with `--step <name>` only when the diff touches its own paths (any of them also when its own script under `packages/astraeus-site/tools/validate/` changes):
    - `synthetic-journey` (phone shell and panels): `packages/astraeus/src/shell/` (`phoneLayout.ts`, `panels/`, the panel and drawer components), `packages/astraeus-site/src/synthetic/syntheticJourneyScene.ts`, `browser-smoke.mjs`.
    - `views` (camera and view code): the Camera paths above, `packages/astraeus/src/api/planViews.ts`, `views.ts`, `viewerViews.ts`, `packages/astraeus/src/shell/viewCamera.ts`, `packages/astraeus-site/src/synthetic/syntheticViewsScene.ts`, `journey-views.mjs`.
    - `meteor-shower` (story panels and showers): `packages/astraeus/src/api/planStory.ts`, `story.ts`, `packages/astraeus/src/presentation/storyPanels.ts`, `packages/astraeus/src/shell/StoryPanelView.tsx`, `storyPanels.ts`, `useStoryPanels.ts`, `packages/astraeus-demo-showers/`, `packages/astraeus-site/src/showerSwitch.ts`, `journey-meteor-shower.mjs`.
    - `two-viewers` (more than one viewer on a page, and what a viewer frees when it goes): `packages/astraeus/src/app/AstraeusScene.tsx`, `LayeredRender.tsx`, `sceneHooks.ts`, `sceneContentsHooks.ts`, `bodyDraw.ts`, `dotMaterial.ts`, `useBodyTexture.ts`, a `dispose` in any view class under `packages/astraeus/src/app/` (`*View.ts`, `*View.tsx`, `KeplerPoints.ts`), `disposeOwned.ts`, `loadingWakes.ts`, `packages/astraeus/src/api/mount.ts`, `packages/astraeus-site/src/synthetic/syntheticTwoViewers.ts`, `journey-two-viewers.mjs`.
    - `group-labels` (host labels on the dots of groups, and the group names they replace): `packages/astraeus/src/app/SceneLabels.ts`, `hostLabels.ts`, `groupLabelPoint.ts`, `GroupSetTarget.ts`, `packages/astraeus/src/api/labelInput.ts`, `planLabels.ts`, `packages/astraeus-site/src/synthetic/syntheticGroupLabelsScene.ts`, `journey-group-labels.mjs`.
    - `orbit-lines` (orbit lines staying on their body, O-099; owner 2026-11-23: full tier, run when orbit-line code changes): `packages/astraeus/src/app/PathView.ts`, `orbitLineRule.ts`, `OrbitSetView.ts`, `pathRules.ts`, `packages/astraeus/src/api/sunOrbit.ts`, `packages/astraeus/src/core/sunCentredSources.ts`, the made-up belt scene in `packages/astraeus-site/src/synthetic/`, `browser-smoke.mjs`.
    - `catalogue` (the component catalogue page): `packages/astraeus-site/components.html`, `packages/astraeus-site/src/catalogue/`, `packages/astraeus-site/data/shelf-catalogue.json`, `packages/astraeus/src/shelf/`, `journey-catalogue.mjs`.
  - The four packed example steps (`hello-scene`, `hello-react`, `hello-planets`, `hello-sky`) run in a Full Objective Check only when the diff touches packaging (the Packaging paths above), `examples/` or the public API surface (`packages/astraeus/src/api/index.ts`, or a change to `packages/astraeus/api-surface.lock.json`, which moves with every change to the root exports): the checker then leaves out `--skip-examples`. A release always runs them (the full tier, and `publish.yml` before publishing).
  - "One browser run per Objective Check" keeps its meaning: one command, once. Never run it twice for one change; a later check reuses the earlier run (owner, 2026-10-20: "Didnt we say we WOULDNT run these checks isnt that the point of this objective"). There are no demo sets.
  - A Task that changes a browser script or the runner runs only the affected steps with `npm run check:browser -- --step <name>` (repeatable); no other per-Task browser runs. A change to a shared file under `packages/astraeus-site/tools/validate/` (`driver.mjs`, `harness.mjs`, `runner.mjs`) affects every step whose script calls the changed function: find them by searching the step scripts for that function name, and run those steps before hand-off, also under orchestration (G-024 Workflow Review; I-192 and I-184 were both first seen at the Full Check). Screen parts, scene sums and demo rules are proved in the fast suite (`npm test`).
  - Headless runs never replace the owner's visual judgement where an Objective requires it.
- **Browser checks never take or save screenshots** (owner, 2026-10-18, T-102). A check that must prove something is drawn reads the scene's own readouts through `packages/astraeus-site/tools/validate/driver.mjs`; the driver guard fails any `.screenshot(` call. The owner judges looks on the preview (`localhost:5490`).
- **The owner preview is `npm run preview:owner`** (I-201, owner 2026-11-22 "can we clean this up so it never happens again"). It replaces an earlier preview started the same way, starts the site dev server on `localhost:5490` with a fresh dependency cache, and restarts it whenever the checkout's branch or commit changes, so the owner never sees a stale or mixed build. Start it fresh before every owner look. To compare with older code, never switch, detach or stash the main checkout while the owner may be looking; use a separate `git worktree` on another port, or a test.
- **Browser regression maintenance.** When a UI change breaks a browser script, update it or name a runnable replacement and map each prior scenario in the map.
  - When a change removes, loosens or moves a browser assertion, the Task evidence lists each affected scenario and where it is now checked, and the Check reviews that list against the scenario map.
- **Browser scripts use the shared interface driver.** Scripts under `tools/validate/` touch the interface only through `packages/astraeus-site/tools/validate/driver.mjs`; an interface change is repaired there, never in the scripts. `driver-guard.mjs`, run by `tests/browserDriverGuard.test.ts`, fails the tests on direct selectors or clicks (O-020 T-083).
- **Historical evidence preservation.** Fresh browser validation writes to a distinct run directory rather than overwriting earlier results. Record the output path, command, time and result; any deliberate replacement of a cited run folder needs an explicit owner decision.
- **Evidence retention (O-037 T-123, owner 2026-10-21).** A browser run keeps only `summary.txt` and each step's `results.json` under `docs/evidence/browser-<stamp>/`; step logs and server logs go to a scratch folder whose path the summary prints. A run folder no Check, Task, Issue or Design note cites may be removed at the next clean-up; a cited folder is kept whole.
